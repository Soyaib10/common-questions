## ভূমিকা: ডেটাবেস মাইগ্রেশন কেন প্রয়োজন?

আপনি যখন একটি ওয়েব অ্যাপ্লিকেশন বা সফটওয়্যার তৈরি করেন, তখন আপনার ডেটাবেসের টেবিলের গঠন (স্কিমা) সময়ের সাথে সাথে পরিবর্তিত হয়। নতুন ফিচার যোগ করতে গেলে নতুন টেবিল বা কলাম যোগ করতে হয়, কখনো পুরোনো কলাম মুছে ফেলতে হয় অথবা ডেটা টাইপ পরিবর্তন করতে হয়। ডেভেলপমেন্টের সময় এই পরিবর্তনগুলো যদি আপনি ম্যানুয়ালি SQL কমান্ড লিখে করে যান, তবে কয়েকটি বড় সমস্যা দেখা দেয়:

1. **সমন্বয়হীনতা**: আপনার সহকর্মীরা জানেন না আপনি কী পরিবর্তন করেছেন। ফলে তাদের লোকাল ডেটাবেসে একই কাঠামো থাকে না এবং অ্যাপ্লিকেশন অপ্রত্যাশিত আচরণ করে।
2. **ইতিহাস সংরক্ষণের অভাব**: আপনি ঠিক কখন কোন পরিবর্তন করেছিলেন, তার কোনো রেকর্ড থাকে না। প্রয়োজনে আগের অবস্থায় ফিরে যাওয়া কঠিন হয়।
3. **উৎপাদন পরিবেশে ঝুঁকি**: সরাসরি প্রোডাকশন ডেটাবেসে হাত দিয়ে SQL চালানো অত্যন্ত বিপজ্জনক এবং পেশাদারিত্বের পরিপন্থী।

**সমাধান: ডেটাবেস মাইগ্রেশন টুল**  
`golang-migrate` এমন একটি টুল যা আপনার ডেটাবেসের স্কিমা পরিবর্তনগুলোকে ভার্সন কন্ট্রোলের আওতায় আনে। এটি Git-এর মতো কাজ করে: আপনি ছোট ছোট `.sql` ফাইলে পরিবর্তনগুলো লিখে রাখেন এবং টুলটি সেগুলোকে ক্রমানুসারে (Sequential) ডেটাবেসে প্রয়োগ করে। এটি নিজেই একটি বিশেষ টেবিলে (`schema_migrations`) রেকর্ড রাখে যে সর্বশেষ কোন ভার্সন পর্যন্ত কাজ হয়েছে।

## পর্ব ১: ইনস্টলেশন ও প্রাথমিক সেটআপ

### প্রশ্ন: উবুন্টুতে কিভাবে সঠিকভাবে গোলাং মাইগ্রেট ইনস্টল করতে হয় যাতে PostgreSQL কাজ করে?

**ঘটনা বিশ্লেষণ:**
আপনি প্রথমে `migrate` কমান্ডটি ব্যবহার করে ডেটাবেসে কানেক্ট করতে গিয়ে এই ত্রুটি দেখতে পেয়েছিলেন:
```
error: failed to open database: database driver: unknown driver postgres (forgotten import?)
```

**কারণ ব্যাখ্যা:**
`migrate` টুলটি যখন আপনি সাধারণভাবে ইনস্টল করেন (যেমন `go install` ব্যবহার করে কোনো ট্যাগ ছাড়া), তখন এটি একটি খালি কাঠামো (Bare-bones binary) তৈরি করে। এটি জানে না আপনি কোন ডেটাবেস (PostgreSQL, MySQL, SQLite ইত্যাদি) ব্যবহার করতে চান। তাই এটিকে বলে দিতে হয় যে PostgreSQL ড্রাইভারটি অন্তর্ভুক্ত করতে হবে।

**সমাধান (বিস্তারিত ধাপ):**

1. **পূর্বে ইনস্টল করা টুলের অবস্থান চেক:**
   ```bash
   which migrate
   # আউটপুট: /home/zihad10/go/bin/migrate
   ```

2. **PostgreSQL ড্রাইভারসহ পুনরায় ইনস্টল:**
   ```bash
   go install -tags 'postgres' github.com/golang-migrate/migrate/v4/cmd/migrate@latest
   ```
   - `-tags 'postgres'`: এটি কম্পাইলারকে বলে যে PostgreSQL ড্রাইভার যুক্ত করতে।
   - এই কমান্ডটি `github.com/lib/pq` ডাউনলোড করবে, যা PostgreSQL-এর সাথে যোগাযোগের জন্য প্রয়োজনীয়।
   - পুরোনো বাইনারি একই স্থানে প্রতিস্থাপিত হবে, কোনো দ্বন্দ্ব (Conflict) হবে না।

3. **যাচাই:**
   ```bash
   migrate -version
   # সংস্করণ নম্বর দেখাবে, এবং ত্রুটি দেখাবে না।
   ```

## পর্ব ২: প্রথম মাইগ্রেশন তৈরি ও চালানো

### প্রশ্ন: কিভাবে প্রথম মাইগ্রেশন ফাইল তৈরি করে একটি টেবিল তৈরি করব?

**পদক্ষেপ ও প্যাটার্ন বিশ্লেষণ:**

1. **মাইগ্রেশন ফাইল জেনারেট করা:**
   ```bash
   migrate create -ext sql -dir migrations create_user_table
   ```
   - **প্যাটার্ন**: `migrate create -ext <extension> -dir <folder> <name>`
   - **ফলাফল**: `migrations` ফোল্ডারে দুটি ফাইল তৈরি হয়:
     - `{timestamp}_create_user_table.up.sql`
     - `{timestamp}_create_user_table.down.sql`

2. **`.up.sql` ফাইলের কাজ:**  
   এই ফাইলে আপনি সেই SQL কমান্ডগুলো লিখবেন যা ডেটাবেসের স্কিমাকে সামনের দিকে নিয়ে যায় (যেমন নতুন টেবিল তৈরি, কলাম যোগ)। উদাহরণ:
   ```sql
   CREATE TABLE users (
       id SERIAL PRIMARY KEY,
       username VARCHAR(50) UNIQUE NOT NULL,
       email VARCHAR(100) UNIQUE NOT NULL
   );
   ```

3. **`.down.sql` ফাইলের কাজ:**  
   এই ফাইলে **বিপরীত কাজ** (Rollback) করার কমান্ড লিখতে হবে। উপরের টেবিল তৈরির বিপরীত হলো টেবিলটি মুছে ফেলা:
   ```sql
   DROP TABLE IF EXISTS users;
   ```

4. **মাইগ্রেশন রান করা:**
   ```bash
   migrate -path migrations -database "postgres://postgres:postgres@localhost:5432/migrate_demo?sslmode=disable" up
   ```
   - **আউটপুট ব্যাখ্যা**:
     - যদি সফল হয়, কিছুই দেখায় না (Silent Success)।
     - `no change` দেখায় যদি এই ভার্সনটি ইতিমধ্যেই প্রয়োগ করা হয়ে থাকে।

5. **ডেটাবেসে ফলাফল যাচাই:**
   ```bash
   sudo -u postgres psql -d migrate_demo
   \dt
   ```
   - আপনি `users` এবং `schema_migrations` নামে দুটি টেবিল দেখতে পাবেন।

## পর্ব ৩: `schema_migrations` টেবিল ও ভার্সনিং-এর রহস্য

### প্রশ্ন: মাইগ্রেশন টুল কিভাবে মনে রাখে কোন কাজগুলো শেষ হয়েছে? `dirty` কলামের কাজ কী?

**গভীর বিশ্লেষণ:**

- **`schema_migrations` টেবিল:**  
  এই টেবিলটি হলো গোলাং মাইগ্রেট টুলের **"মস্তিষ্ক"**। যখনই আপনি `up` বা `down` কমান্ড চালান, টুলটি সর্বপ্রথম এই টেবিলে উঁকি দেয়।

- **কলাম দুটি:**
  1. **`version`**: এটি একটি বড় সংখ্যা (আপনার মাইগ্রেশন ফাইলের নামের টাইমস্ট্যাম্প)। এটি নির্দেশ করে বর্তমানে ডেটাবেস কত নম্বর ভার্সনে আছে।
  2. **`dirty`**: এটি একটি বুলিয়ান মান (`t` বা `f`)।

- **`dirty` কলামের ভূমিকা (নিরাপত্তা কবজা):**
  - যখন আপনি একটি মাইগ্রেশন কমান্ড দেন (যেমন `up`), টুলটি কাজ শুরু করার **আগেই** এই কলামটিকে `true` করে দেয়।
  - এর অর্থ: "আমি এখন ডেটাবেসে কাজ করছি, কেউ অন্য কোনো কমান্ড দিও না।"
  - যদি আপনার `.sql` ফাইলে কোনো **ভুল** থাকে (যেমন বানান ভুল: `CREATE TABLEEEE`), অথবা মাঝপথে নেটওয়ার্ক বিচ্ছিন্ন হয়, তাহলে কাজটি অসম্পূর্ণ থেকে যায় এবং `dirty` কলামটি `true` অবস্থায় আটকে যায়।
  - **গুরুত্বপূর্ণ**: ডেটাবেস একবার `dirty` হয়ে গেলে, আপনি সঠিক SQL ফাইল দিয়েও আর কোনো মাইগ্রেশন (`up` বা `down`) চালাতে পারবেন না। এটি একটি সুরক্ষা ব্যবস্থা যাতে অর্ধ-পরিবর্তিত অবস্থায় আরও ক্ষতি না হয়।

## পর্ব ৪: ত্রুটি ও `dirty` অবস্থা থেকে উদ্ধার (The `force` Command)

### প্রশ্ন: মাইগ্রেশন ফাইলে ভুল করার পর `dirty` অবস্থা কিভাবে ঠিক করব?

**ঘটনা প্রবাহ ও সমাধান:**

1. **সমস্যা তৈরি:** আপনি ইচ্ছাকৃতভাবে `.up.sql` ফাইলে ভুল লিখলেন (`CREATE TABLEEEE...`) এবং `up` কমান্ড দিলেন। টুলটি ত্রুটি দেখালো এবং `schema_migrations` টেবিলে `dirty` কলাম `true` হয়ে গেল।

2. **সমাধানের ধাপ (কখনোই এড়িয়ে যাবেন না):**
   - **ধাপ ১:** আপনার `.sql` ফাইলের ভুলটি ঠিক করুন।
   - **ধাপ ২:** `force` কমান্ড ব্যবহার করে টুলটিকে বলুন যে ভুলটি ঠিক করা হয়েছে এবং সে যেন এই ভার্সনটিকে সফল বলে ধরে নেয়।
     ```bash
     migrate -path migrations -database "postgres://..." force {timestamp}
     ```
   - **`force` কমান্ডের সীমাবদ্ধতা:**  
     এই কমান্ডটি **কোনো SQL ফাইল চালায় না**। এটি শুধু `schema_migrations` টেবিলের `dirty` কলামটি `false` করে এবং ভার্সন নম্বর আপডেট করে।

3. **জটিলতা ও পরিষ্কারকরণ:**
   - যেহেতু `force` SQL চালায় না, আপনার টেবিলটি কিন্তু তৈরি হয়নি, অথচ টুলটি ভাবছে হয়ে গেছে। ফলে আবার `up` দিলে সে বলবে `no change`।
   - **সঠিক পদক্ষেপ:**
     - ট্র্যাকারটিকে এক ধাপ পিছিয়ে দিন: `migrate ... force 0` (এটি বলে আপনি এখন শূন্য অবস্থায় আছেন)।
     - তারপর আবার সঠিক SQL সহ `up` কমান্ড দিন।
     - এবার টুলটি ফাইল থেকে কোড পড়ে সঠিকভাবে টেবিল তৈরি করবে।

---

## পর্ব ৫: ক্রমানুসারে মাইগ্রেশন (Sequential Execution)

### প্রশ্ন: আমি যদি দ্বিতীয় একটি মাইগ্রেশন ফাইল তৈরি করি, তাহলে আগের ফাইলটির কী হবে?

**প্যাটার্ন বিশ্লেষণ ও পরীক্ষা:**

- **দ্বিতীয় মাইগ্রেশন তৈরি:**
  ```bash
  migrate create -ext sql -dir migrations add_bio_to_users
  ```
  - `.up.sql`: `ALTER TABLE users ADD COLUMN bio TEXT;`
  - `.down.sql`: `ALTER TABLE users DROP COLUMN bio;`

- **চালানোর পর যা ঘটে:**
  আপনি যখন আবার `migrate ... up` কমান্ড দেন, টুলটি নিচের কাজগুলো ক্রমানুসারে করে:
  1. `schema_migrations` টেবিল চেক করে দেখে বর্তমান ভার্সন ১।
  2. ফোল্ডারে ফাইল দেখে: ভার্সন ১ (ইউজার টেবিল), ভার্সন ২ (বায়ো কলাম)।
  3. **সে সরাসরি ২ নম্বরে লাফ দেয় না।** সে ১ থেকে ২-এ যাওয়ার জন্য **শুধুমাত্র ২ নম্বর ফাইলটি** রান করে।
  4. সবশেষে `schema_migrations` টেবিলের ভার্সন নম্বর আপডেট করে ২ করে দেয়।

- **গুরুত্বপূর্ণ অন্তর্দৃষ্টি:**  
  আপনি যদি ২ নম্বর মাইগ্রেশন `down` করেন (`migrate ... down 1`), তাহলে টুলটি **শুধুমাত্র ২ নম্বর ফাইলের `.down.sql`** রান করবে। আপনার `users` টেবিলটি অক্ষত থাকবে, শুধু `bio` কলামটি মুছে যাবে এবং ভার্সন আবার ১ হয়ে যাবে।

## পর্ব ৬: বিদ্যমান ডেটাসহ বাধ্যতামূলক (NOT NULL) কলাম যোগ করার কৌশল

### প্রশ্ন: টেবিলে আগে থেকেই ৫টি ডাটা (Row) আছে। এখন আমি একটি নতুন কলাম যোগ করতে চাই যা `NOT NULL` হবে। কিন্তু আগের সারিগুলোতে তো এই কলামের কোনো মান নেই। এটা কিভাবে সম্ভব?

**সমস্যা বিশ্লেষণ:**
আপনি যদি সরাসরি এই কমান্ড দেন:
```sql
ALTER TABLE users ADD COLUMN phone VARCHAR(15) NOT NULL;
```
PostgreSQL ত্রুটি দেবে: `ERROR: column "phone" contains null values`। কারণ সে জানে না আগের সারিগুলোর জন্য `phone` কলামে কী বসাতে হবে।

**তিনটি পদ্ধতি ও তাদের বিস্তারিত ব্যাখ্যা:**

#### পদ্ধতি ১: ডিফল্ট মান ব্যবহার করা (সহজ পন্থা)
- **কৌশল:** কলাম তৈরির সময় একটি ডিফল্ট মান (`DEFAULT`) দিয়ে দেওয়া।
- **SQL:**
  ```sql
  ALTER TABLE users ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'active';
  ```
- **ফলাফল:** নতুন কলামে আগের সব সারির জন্য স্বয়ংক্রিয়ভাবে `'active'` বসে যাবে।
- **সুবিধা:** এক লাইনের কাজ, দ্রুত সমাধান।
- **অসুবিধা:** ডিফল্ট মানটি স্থায়ীভাবে থেকে যায় এবং সব নতুন ইউজারের জন্য এটি প্রযোজ্য হবে।

#### পদ্ধতি ২: ধাপে ধাপে মাইগ্রেশন (পেশাদার পন্থা - সুপারিশকৃত)
- **কৌশল:** একই মাইগ্রেশন ফাইলের ভেতরে তিনটি ধাপে কাজটি সম্পন্ন করা।
- **SQL (`.up.sql`):**
  ```sql
  -- ধাপ ১: প্রথমে NULL অনুমতি দিয়ে কলাম তৈরি
  ALTER TABLE users ADD COLUMN phone VARCHAR(15);

  -- ধাপ ২: আগের ফাঁকা সারিগুলো আপডেট করা
  UPDATE users SET phone = '000-000-0000' WHERE phone IS NULL;

  -- ধাপ ৩: এখন কলামটিকে NOT NULL করে দেওয়া
  ALTER TABLE users ALTER COLUMN phone SET NOT NULL;
  ```
- **ফলাফল:** কোনো ত্রুটি ছাড়াই মাইগ্রেশন সফল হবে। আগের ডাটাগুলোতে আপনার দেওয়া মান (`'000-000-0000'`) বসে যাবে এবং নতুন ডাটার জন্য কলামটি বাধ্যতামূলক হবে।
- **সুবিধা:** আপনি নির্দিষ্ট করে দিতে পারেন পুরোনো ডাটার জন্য কী মান হবে, এবং ভবিষ্যতের ডাটার জন্য ডাটাবেস লেভেলেই নিশ্চয়তা পাবেন।

#### পদ্ধতি ৩: অ্যাপ্লিকেশন স্তরে নিয়ন্ত্রণ (ডেটাবেসে NULL অনুমতি দেওয়া)
- **কৌশল:** ডেটাবেসে কলামটি `NULL` রাখার অনুমতি দিয়ে তৈরি করা এবং আপনার Go কোডে চেক করা।
- **SQL (`.up.sql`):**
  ```sql
  ALTER TABLE users ADD COLUMN address TEXT; -- NOT NULL নেই
  ```
- **Go কোডে নিয়ন্ত্রণ:**
  ```go
  if user.Address == "" {
      return errors.New("নতুন ইউজারের জন্য ঠিকানা আবশ্যক")
  }
  ```
- **সুবিধা:** ডেটাবেস মাইগ্রেশন সহজ।
- **অসুবিধা:** ডেটাবেসের নিজস্ব সুরক্ষা বলয় (Integrity Constraint) দুর্বল হয়। কোনো বাগ বা সরাসরি SQL কমান্ডের মাধ্যমে ফাঁকা ঠিকানা ঢুকে যেতে পারে।

**পরীক্ষা ও ফলাফল:**
আপনি যখন পদ্ধতি ২ পরীক্ষা করেছিলেন, তখন দেখেছেন আগের সারিগুলোতে ফোন নম্বর যোগ হয়ে গেছে এবং কোনো ত্রুটি আসেনি। এটিই বাস্তব প্রজেক্টের জন্য সবচেয়ে নির্ভরযোগ্য পদ্ধতি।

## পর্ব ৭: ভুল সংশোধন ও মাইগ্রেশন ফাইল ডিলিট করার বিপদ

### প্রশ্ন: ধরুন আমার ৪টি মাইগ্রেশন ফাইল আছে। আমি যদি দ্বিতীয় ফাইলটি ডিলিট করে দিই, তাহলে কী হবে?

**বিস্তারিত বিশ্লেষণ ও পেশাদার দৃষ্টিভঙ্গি:**

- **সরাসরি ফাইল ডিলিট করলে কী ঘটে?**
  1. **ভার্সন শৃঙ্খল ভেঙে যাওয়া (Version Gap):**  
     টুলটি ক্রমানুসারে (Sequential) ভার্সন আশা করে। সে ফোল্ডারে ১, ৩, ৪ দেখতে পাবে এবং ২ খুঁজে না পেয়ে বিভ্রান্ত হবে। পরবর্তী `up` বা `down` কমান্ড ত্রুটি দেখাতে পারে।
  2. **নির্ভরশীলতার ত্রুটি (Dependency Error):**  
     ধরুন ৩ নম্বর মাইগ্রেশনটি ২ নম্বরে তৈরি করা একটি কলাম ব্যবহার করে। এখন নতুন পরিবেশে (যেমন আপনার সহকর্মীর পিসি) মাইগ্রেশন চালালে, ১ এর পর সরাসরি ৩ রান হবে এবং ত্রুটি দেবে কারণ ওই কলামটি নেই।
  3. **স্টেট মিসম্যাচ (State Mismatch):**  
     আপনার লোকাল ডেটাবেসে কিন্তু ২ নম্বর মাইগ্রেশনটি অলরেডি রান হয়ে গেছে (টেবিলের গঠন পরিবর্তিত হয়েছে)। আপনি ফাইল ডিলিট করলে টেবিলের গঠন আগের অবস্থায় ফিরে যাবে না। ভবিষ্যতে আপনি যদি `down` করতে চান, টুলটি ২ নম্বর ফাইলের `.down.sql` খুঁজে পাবে না এবং রোলব্যাক করতে ব্যর্থ হবে।

- **সঠিক পদ্ধতি (Forward Migration):**
  - **নিয়ম:** কখনোই মাঝখান থেকে কোনো মাইগ্রেশন ফাইল ডিলিট করবেন না।
  - **করণীয়:** আপনি যদি ২ নম্বর মাইগ্রেশনের কাজটি (যেমন একটি কলাম) বাতিল করতে চান, তবে **একটি নতুন মাইগ্রেশন ফাইল (যেমন ৫ নম্বর)** তৈরি করুন এবং সেখানে বিপরীত কাজটি লিখুন।
  - **উদাহরণ:**
    - ২ নম্বরে `phone` কলাম যোগ করা হয়েছিল।
    - এখন আপনি এটি সরাতে চাইলে একটি নতুন মাইগ্রেশন তৈরি করবেন (`remove_phone_column`)।
    - **`.up.sql`**-এ লিখবেন: `ALTER TABLE users DROP COLUMN phone;`
    - **`.down.sql`**-এ লিখবেন: `ALTER TABLE users ADD COLUMN phone VARCHAR(15);` (যদি কখনো ফিরিয়ে আনতে হয়)।

- **মূলমন্ত্র:**  
  মাইগ্রেশন ফাইলগুলোকে একটি **অপরিবর্তনীয় ইতিহাসের খাতা** (Append-only Ledger) হিসেবে ভাবুন। একবার লেখা হয়ে গেলে তা আর মুছবেন না, প্রয়োজনে নতুন এন্ট্রি দিয়ে তার প্রভাব প্রশমিত করবেন।

## 🛠️ Golang Migrate Cheat Sheet

### ১. নতুন মাইগ্রেশন ফাইল তৈরি করা
```bash
migrate create -ext sql -dir migrations <name_of_migration>
# উদাহরণ: migrate create -ext sql -dir migrations add_phone_to_users
```

### ২. মাইগ্রেশন রান করা (Up)
```bash
# সব মাইগ্রেশন ফাইল রান করা
migrate -path migrations -database "postgres://user:pass@localhost:5432/dbname?sslmode=disable" up

# নির্দিষ্ট কয়েক ধাপ সামনে যাওয়া (যেমন ২ ধাপ)
migrate -path migrations -database "..." up 2
```

### ৩. রোলব্যাক বা পেছনে যাওয়া (Down)
```bash
# সব মাইগ্রেশন রিভার্স করা (সাবধান!)
migrate -path migrations -database "..." down

# মাত্র ১ ধাপ বা নির্দিষ্ট ধাপ পেছনে যাওয়া
migrate -path migrations -database "..." down 1
```

### ৪. নির্দিষ্ট ভার্সনে যাওয়া (Goto)
```bash
# সরাসরি কোনো নির্দিষ্ট টাইমস্ট্যাম্প বা ভার্সনে চলে যাওয়া
migrate -path migrations -database "..." goto 20260409092702
```

### ৫. ডার্টি স্টেট (Dirty State) ফিক্স করা
যদি মাইগ্রেশন মাঝপথে এরর দেয় এবং ডেটাবেস 'dirty' হয়ে যায়:
```bash
# প্রথমে .sql ফাইলের ভুল ঠিক করুন, তারপর জোরপূর্বক ভার্সন সেট করুন
migrate -path migrations -database "..." force <version_number>
```

### ৬. সব টেবিল মুছে ফেলা (Drop)
ডেভেলপমেন্টের সময় একদম ফ্রেশ শুরু করার জন্য:
```bash
migrate -path migrations -database "..." drop
```

### ৭. বর্তমান ভার্সন চেক করা
```bash
migrate -path migrations -database "..." version
```

## 💡 কিছু প্রো-টিপস:
* **Sequential Order:** ফাইলগুলো সবসময় নামের শুরুতে থাকা টাইমস্ট্যাম্প অনুযায়ী রান হয়।
* **Up/Down Balance:** সবসময় চেষ্টা করবেন `up.sql`-এ যা তৈরি করছেন, `down.sql`-এ ঠিক তার উল্টোটা রাখতে।
* **Never Delete:** একবার মাইগ্রেশন পুশ বা শেয়ার হয়ে গেলে মাঝখান থেকে কোনো ফাইল ডিলিট করবেন না; সবসময় নতুন মাইগ্রেশন দিয়ে পরিবর্তন আনবেন।

## উপসংহার: Golang Migrate শেখার মূল শিক্ষা ও প্যাটার্ন

1. **ইনস্টলেশন প্যাটার্ন:** নির্দিষ্ট ড্রাইভার ট্যাগসহ টুল ইনস্টল করতে হবে।
2. **কমান্ড প্যাটার্ন:** `migrate create` নতুন ফাইল তৈরি করে, `migrate up` প্রয়োগ করে, `migrate down {N}` পিছিয়ে যায়।
3. **স্টেট ম্যানেজমেন্ট:** `schema_migrations` টেবিল ও `dirty` ফ্ল্যাগ হলো টুলটির আত্মা। ত্রুটি হলে `force` দিয়ে সমাধান করতে হয়।
4. **ক্রমানুসারে কার্য সম্পাদন:** টুলটি সব ফাইল একসাথে রান না করে ধাপে ধাপে রান করে এবং প্রতিটি ধাপ ট্র্যাক করে।
5. **ডেটা সংরক্ষণ কৌশল:** বিদ্যমান ডেটাসহ `NOT NULL` কলাম যোগ করতে ধাপে ধাপে SQL (Add -> Update -> Alter) ব্যবহার করতে হবে।
6. **ইতিহাস সংরক্ষণ নীতি:** কোনো মাইগ্রেশন ফাইল কখনো ডিলিট নয়, বরং পরিবর্তনের জন্য নতুন মাইগ্রেশন তৈরি করতে হবে।
