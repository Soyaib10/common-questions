# Asynq পূর্ণাঙ্গ শিক্ষানোট (বাংলায়)

## সূচনা: Asynq কী এবং এর মৌলিক ধারণা

Asynq হলো Go প্রোগ্রামিং ভাষায় লেখা একটি লাইব্রেরি, যা ব্যাকগ্রাউন্ড টাস্ক প্রক্রিয়াকরণের জন্য ব্যবহৃত হয়। এটি Redis কে মেসেজ ব্রোকার হিসেবে ব্যবহার করে। Asynq-তে মূলত তিনটি প্রধান উপাদান দিয়ে কাজ হয়:

১. **Task (টাস্ক)** — কী করতে হবে তার সংজ্ঞা। একটি টাস্কের দুটি অপরিহার্য অংশ থাকে:
   - **Type:** একটি স্ট্রিং যা টাস্কের ধরন নির্দেশ করে (যেমন: `"email:welcome"`)।
   - **Payload:** একটি বাইট স্লাইস (`[]byte`) যা সাধারণত JSON ফরম্যাটে রাখা হয় এবং কাজটি সম্পন্ন করতে প্রয়োজনীয় ডাটা ধারণ করে (যেমন: ইউজারের আইডি, ইমেইল ঠিকানা)।
২. **Client (ক্লায়েন্ট)** — যে টাস্ক তৈরি করে এবং সেটিকে Redis-এ জমা দেয় (Enqueue করে)।
৩. **Server (সার্ভার)** — যে Redis থেকে টাস্ক তুলে আনে এবং নির্দিষ্ট Handler দিয়ে তা প্রক্রিয়াকরণ (Process) করে।

এখন আমরা এই উপাদানগুলো একে একে বিস্তারিতভাবে দেখব। তবে তার আগে Asynq-তে ব্যবহৃত গুরুত্বপূর্ণ সকল কীওয়ার্ডের একটি টেবিল দেওয়া হলো, যা দ্রুত রেফারেন্সের জন্য কাজে লাগবে।

## ১. Asynq-এর সকল কীওয়ার্ড ও তাদের কার্যাবলি (সারণি)

এখানে Asynq লাইব্রেরির প্রায় সকল গুরুত্বপূর্ণ কীওয়ার্ড, তাদের কাজ এবং সংক্ষিপ্ত উদাহরণ একটি টেবিলের মাধ্যমে উপস্থাপন করা হলো। এই টেবিলটি সম্পূর্ণ Asynq ইকোসিস্টেমের একটি মানচিত্র হিসেবে কাজ করবে।

### Core Types (মূল উপাদান)

| কীওয়ার্ড (Keyword) | কী কাজ করে | ছোট উদাহরণ (Small Example) |
| :--- | :--- | :--- |
| `asynq.NewTask` | টাস্ক তৈরি করে (Type + Payload) | `asynq.NewTask("email:send", payload)` |
| `asynq.NewClient` | Redis-এ টাস্ক পাঠানোর জন্য ক্লায়েন্ট তৈরি করে | `asynq.NewClient(redisOpt)` |
| `asynq.NewServer` | টাস্ক প্রক্রিয়াকরণের জন্য সার্ভার তৈরি করে | `asynq.NewServer(redisOpt, config)` |
| `asynq.NewServeMux` | টাস্কের Type অনুযায়ী সঠিক Handler-এ রাউট করে | `mux := asynq.NewServeMux()` |
| `asynq.NewScheduler` | পর্যায়ক্রমিক (Periodic) টাস্ক নির্ধারিত সময়ে চালানোর জন্য শিডিউলার তৈরি করে | `asynq.NewScheduler(redisOpt, nil)` |
| `asynq.NewInspector` | চলমান কিউ এবং টাস্ক পরিদর্শন (Inspect) করার জন্য ইন্সপেক্টর তৈরি করে | `asynq.NewInspector(redisOpt)` |

### Client Options (Enqueue করার সময় ব্যবহৃত অপশন)

ক্লায়েন্ট যখন টাস্ক জমা করে, তখন এই অপশনগুলো ব্যবহার করে টাস্কের আচরণ নিয়ন্ত্রণ করা যায়।

| কীওয়ার্ড | কী কাজ করে | ছোট উদাহরণ |
| :--- | :--- | :--- |
| `asynq.Queue` | টাস্কটি কোন কিউ-তে যাবে তা নির্ধারণ করে | `client.Enqueue(task, asynq.Queue("critical"))` |
| `asynq.ProcessIn` | কতক্ষণ পরে টাস্কটি প্রক্রিয়াকরণ শুরু হবে তা নির্ধারণ করে | `asynq.ProcessIn(24 * time.Hour)` |
| `asynq.ProcessAt` | ঠিক কোন সময়ে টাস্কটি প্রক্রিয়াকরণ শুরু হবে তা নির্ধারণ করে | `asynq.ProcessAt(time.Now().Add(1*time.Hour))` |
| `asynq.MaxRetry` | ব্যর্থ হলে সর্বোচ্চ কতবার পুনরায় চেষ্টা (Retry) করবে তা নির্ধারণ করে | `asynq.MaxRetry(5)` |
| `asynq.Timeout` | টাস্ক প্রক্রিয়াকরণের জন্য হ্যান্ডলার সর্বোচ্চ কতক্ষণ সময় পাবে তা নির্ধারণ করে | `asynq.Timeout(30 * time.Second)` |
| `asynq.Deadline` | নির্দিষ্ট সময়সীমার মধ্যে টাস্ক প্রক্রিয়াকরণ শেষ করতে হবে, অন্যথায় ব্যর্থ বলে গণ্য হবে | `asynq.Deadline(time.Date(...))` |
| `asynq.Unique` | নির্দিষ্ট সময়ের জন্য একই ধরনের টাস্ক কিউতে দ্বিতীয়বার ঢুকতে বাধা দেয় (ডুপ্লিকেট প্রতিরোধ) | `asynq.Unique(time.Hour)` |
| `asynq.TaskID` | টাস্কের জন্য একটি কাস্টম ইউনিক আইডি নির্ধারণ করে, যা ডুপ্লিকেট কঠোরভাবে প্রতিরোধে সাহায্য করে | `asynq.TaskID("my-unique-id")` |
| `asynq.Retention` | টাস্ক সফলভাবে সম্পন্ন হওয়ার পর কতক্ষণ Redis-এ সংরক্ষিত থাকবে তা নির্ধারণ করে | `asynq.Retention(24 * time.Hour)` |
| `asynq.Group` | টাস্ক অ্যাগ্রিগেশনের জন্য গ্রুপ নাম নির্ধারণ করে | `asynq.Group("user1:notifications")` |

### Server Config (সার্ভার কনফিগারেশন)

সার্ভার চালু করার সময় এই কনফিগারেশনগুলো ব্যবহার করা হয়।

| কীওয়ার্ড | কী কাজ করে | ছোট উদাহরণ |
| :--- | :--- | :--- |
| `asynq.Config.Concurrency` | একই সাথে সর্বোচ্চ কতজন ওয়ার্কার টাস্ক প্রক্রিয়া করবে তা নির্ধারণ করে | `Concurrency: 10` |
| `asynq.Config.Queues` | একাধিক কিউ এবং তাদের অগ্রাধিকার (Priority) নির্ধারণ করে | `Queues: map[string]int{"critical":6, "default":3}` |
| `asynq.Config.StrictPriority` | স্ট্রিক্ট অগ্রাধিকার মোড চালু করে। এতে উচ্চ অগ্রাধিকারের কিউ খালি না হওয়া পর্যন্ত নিম্ন অগ্রাধিকারের কিউ থেকে টাস্ক নেওয়া হয় না | `StrictPriority: true` |
| `asynq.Config.RetryDelayFunc` | পুনরায় চেষ্টা (Retry) এর মধ্যবর্তী বিলম্ব কীভাবে গণনা করা হবে তা নির্ধারণের জন্য কাস্টম ফাংশন | `func(n int, e error, t *asynq.Task) time.Duration { ... }` |
| `asynq.Config.IsFailure` | কোনো error-কে প্রকৃত ব্যর্থতা (Failure) হিসেবে গণ্য করা হবে কি না, তা নির্ধারণের জন্য কাস্টম ফাংশন | `func(err error) bool { ... }` |
| `asynq.Config.GroupAggregator` | টাস্ক অ্যাগ্রিগেশন কীভাবে হবে তার লজিক নির্ধারণ করে | `GroupAggregatorFunc(aggregateFunc)` |
| `asynq.Config.GroupGracePeriod` | অ্যাগ্রিগেশনের জন্য গ্রেস পিরিয়ড। নতুন টাস্ক আসা বন্ধ হওয়ার পর এই সময় অপেক্ষা করে | `GroupGracePeriod: 2*time.Minute` |
| `asynq.Config.GroupMaxDelay` | অ্যাগ্রিগেশনের জন্য সর্বোচ্চ বিলম্ব। এই সময় পরে জোর করে অ্যাগ্রিগেশন করা হয় | `GroupMaxDelay: 10*time.Minute` |
| `asynq.Config.GroupMaxSize` | একসাথে সর্বোচ্চ কতটি টাস্ক অ্যাগ্রিগেট হবে তা নির্ধারণ করে | `GroupMaxSize: 20` |

### Handler Related (হ্যান্ডলার সংক্রান্ত)

| কীওয়ার্ড | কী কাজ করে | ছোট উদাহরণ |
| :--- | :--- | :--- |
| `asynq.Handler` | একটি ইন্টারফেস। `ProcessTask` মেথড ইমপ্লিমেন্ট করতে হয় | `type MyHandler struct{}; func (h *MyHandler) ProcessTask(...) error` |
| `asynq.HandlerFunc` | একটি সাধারণ ফাংশনকে হ্যান্ডলার টাইপে রূপান্তর করে | `asynq.HandlerFunc(myFunc)` |
| `mux.Handle` | একটি নির্দিষ্ট টাস্ক টাইপের সাথে হ্যান্ডলার নিবন্ধন করে | `mux.Handle("email:send", handler)` |
| `mux.HandleFunc` | একটি নির্দিষ্ট টাস্ক টাইপের সাথে ফাংশন নিবন্ধন করে | `mux.HandleFunc("email:send", myFunc)` |
| `mux.Use` | সার্ভ মাক্সে মিডলওয়্যার যুক্ত করে | `mux.Use(loggingMiddleware)` |
| `asynq.SkipRetry` | এই error রিটার্ন করলে টাস্কটি আর রিট্রাই হবে না, সরাসরি আর্কাইভ স্টেটে চলে যাবে | `return fmt.Errorf("bad data: %w", asynq.SkipRetry)` |

### Scheduler Related (শিডিউলার সংক্রান্ত)

| কীওয়ার্ড | কী কাজ করে | ছোট উদাহরণ |
| :--- | :--- | :--- |
| `scheduler.Register` | ক্রন এক্সপ্রেশন অনুযায়ী টাস্ক নিবন্ধন করে | `scheduler.Register("* * * * *", task)` |
| `scheduler.Run` | শিডিউলার চালু করে | `scheduler.Run()` |

### Error Types (ত্রুটির ধরন)

| কীওয়ার্ড | কী কাজ করে |
| :--- | :--- |
| `asynq.ErrDuplicateTask` | `Unique` অপশন থাকা সত্ত্বেও একই টাস্ক আবার জমা দিলে এই error আসে |
| `asynq.ErrTaskIDConflict` | একই `TaskID` দিয়ে আবার টাস্ক জমা দিলে এই error আসে |

এটাই হলো Asynq-এর প্রায় সকল গুরুত্বপূর্ণ উপাদানের তালিকা। এবার আমরা প্রতিটি অংশ গভীরভাবে এবং ধাপে ধাপে দেখব।

## ২. Client (ক্লায়েন্ট) বিস্তারিত ব্যাখ্যা ও বাস্তব উদাহরণ

ক্লায়েন্টের কাজ হলো একটি মাত্র: **Enqueue** করা। অর্থাৎ একটি টাস্ক তৈরি করে সেটিকে Redis-এর কিউতে পাঠিয়ে দেওয়া। এর চেয়ে বেশি কিছু ক্লায়েন্ট করে না। একটি বাস্তব উদাহরণের মাধ্যমে এটি বোঝা যাক।

ধরো তুমি একটি পোস্ট অফিসে গিয়ে একটি চিঠি পাঠাতে চাও। তুমি যা করবে:
১. কাউন্টারে যাবে।
২. চিঠিটি দেবে।
৩. বলবে "এটি চট্টগ্রামে পাঠাও।"
৪. চলে আসবে।

তোমার কাজ সেখানেই শেষ। চিঠিটি কখন পৌঁছাবে, কে পৌঁছে দেবে— সে বিষয়ে তুমি কিছু জানো না বা জানার প্রয়োজনও নেই। এখানে:
- **তুমি** = Client
- **পোস্ট অফিস কাউন্টার** = `client.Enqueue()` মেথড
- **চিঠি** = Task
- **চট্টগ্রাম** = Queue

এবার আসি কোডে। ধরো তুমি একটি Go প্রোগ্রাম লিখছ যা ইমেইল পাঠানোর কাজটিকে ব্যাকগ্রাউন্ডে পাঠিয়ে দেবে। নিচের কোডটি দেখো:

```go
package main

import (
    "encoding/json"
    "fmt"
    "log"
    "github.com/hibiken/asynq"
)

func main() {
    // ধাপ ১: পোস্ট অফিসে যাওয়া। অর্থাৎ Redis-এর সাথে সংযোগ স্থাপন।
    client := asynq.NewClient(asynq.RedisClientOpt{
        Addr: "localhost:6379", // Redis সার্ভারের ঠিকানা
    })
    defer client.Close() // প্রোগ্রাম শেষে ক্লায়েন্ট সংযোগ বন্ধ করা

    // ধাপ ২: চিঠি লেখা। অর্থাৎ টাস্কের Payload তৈরি করা, যেখানে প্রয়োজনীয় ডাটা থাকবে।
    payload, err := json.Marshal(map[string]interface{}{
        "user_id": 42,
        "email":   "rahim@example.com",
    })
    if err != nil {
        log.Fatal(err)
    }

    // ধাপ ৩: চিঠি খামে ভরা। অর্থাৎ টাস্ক তৈরি করা, যেখানে Type ও Payload থাকে।
    task := asynq.NewTask("email:welcome", payload)

    // ধাপ ৪: পোস্ট অফিসে জমা দেওয়া। অর্থাৎ Redis কিউতে টাস্কটি পাঠানো।
    info, err := client.Enqueue(task)
    if err != nil {
        log.Fatal(err)
    }

    // পোস্ট অফিসের রশিদ (Receipt) প্রিন্ট করা
    fmt.Printf("Task ID: %s\n", info.ID)
    fmt.Printf("Queue: %s\n", info.Queue)
    fmt.Printf("State: %s\n", info.State)
}
```

উপরের প্রোগ্রামটি চালালে নিচের মত আউটপুট আসবে (আইডি ভিন্ন হতে পারে):
```
Task ID: c0b2a0a0-5678-...
Queue: default
State: pending
```
এর অর্থ: টাস্কটি Redis-এ জমা হয়েছে, `default` নামক কিউতে আছে, এবং এখনো কেউ সেটি তুলে নেয়নি বলে তার অবস্থা `pending`।

এখন একটি গুরুত্বপূর্ণ প্রশ্ন: `asynq.NewTask("email:welcome", payload)` — এখানে `"email:welcome"` স্ট্রিংটির অর্থ কী? এটি কে ব্যবহার করে এবং কেন এই ফরম্যাটে লেখা হয়?

**উত্তর:**
`"email:welcome"` হলো টাস্কের **Type**। এটি একটি স্ট্রিং যা টাস্কের পরিচয় বহন করে। সার্ভার যখন এই টাস্কটি পায়, তখন এই স্ট্রিংটি দেখেই বুঝতে পারে যে এটি কোন ধরণের কাজ এবং এটি প্রক্রিয়া করার জন্য কোন হ্যান্ডলারকে ডাকা উচিত। ঠিক যেমন একটি খামের উপরে "Speed Post" বা "Registered Post" লেখা থাকে, যাতে ডাকবিভাগ বুঝতে পারে কীভাবে এটি হ্যান্ডেল করতে হবে।

এখন প্রশ্ন হলো, `"email:welcome"`-এ কোলন (`:`) দিয়ে লেখার কারণ কী? এটি Asynq-এর একটি কনভেনশন এবং একটি শক্তিশালী ফিচার। এটি বাধ্যতামূলক নয়, তবে এই ফরম্যাটে লেখার একটি বিশেষ সুবিধা আছে। তুমি সার্ভারের `ServeMux`-এ প্রিফিক্স ম্যাচিং (Prefix Matching) করতে পারবে। যেমন:

```go
mux.Handle("email:", defaultEmailHandler) // যেকোনো "email:" দিয়ে শুরু হওয়া টাইপ এখানে আসবে
mux.Handle("email:welcome", welcomeHandler) // নির্দিষ্ট টাইপটি এখানে আসবে
```
এর মানে হলো, `"email:"` দিয়ে রেজিস্টার করলে `"email:welcome"`, `"email:reminder"`, `"email:reset"` ইত্যাদি সব টাস্ক প্রথম হ্যান্ডলারটিতে যাবে। এটি একটি ফাইনাল প্যাটার্ন, যা রাউটিংকে অনেক সহজ করে তোলে।

**প্যাকিং প্রক্রিয়া (Packing Process):**
যখন তুমি `client.Enqueue(task)` কল করো, ক্লায়েন্ট অভ্যন্তরীণভাবে তোমার দেওয়া টাস্ক অবজেক্টটিকে একটি সম্পূর্ণ JSON মেসেজে রূপান্তর করে। এটি দেখতে অনেকটা এরকম:

```json
{
    "type": "email:welcome",
    "payload": {"user_id": 42, "email": "rahim@example.com"},
    "id": "c0b2a0a0-1234-...",
    "queue": "default",
    "retry": 25,
    "timeout": 1800
}
```
অর্থাৎ, শুধু তোমার Type ও Payload নয়, Asynq নিজে থেকে আরও কিছু জিনিস যোগ করে দেয়, যেমন একটি ইউনিক আইডি, কোন কিউতে যাবে, কতবার রিট্রাই হবে, টাইমআউট কত, ইত্যাদি। এই পুরো জিনিসটি JSON আকারে Redis-এ সংরক্ষিত হয়। কেন এটা জানা দরকার? কারণ সার্ভার যখন এই টাস্ক তুলবে, সে এই পুরো JSON পড়বে এবং Type দেখে বুঝবে কোন হ্যান্ডলারকে ডাকতে হবে, আর Payload দেখে বুঝবে কী ডাটা পাঠানো হয়েছে।

## ৩. Server (সার্ভার) ও Handler (হ্যান্ডলার) বিস্তারিত ব্যাখ্যা

সার্ভার হলো সেই ডেলিভারি ম্যান, যে পোস্ট অফিস (Redis) থেকে চিঠি (Task) তুলে আনে এবং গন্তব্যে পৌঁছে দেয় (Process করে)।

সার্ভার চালু করতে তিনটি জিনিস লাগে:
১. **Redis সংযোগ:** কোথা থেকে টাস্ক তুলে আনবে।
২. **Config:** কতজন ওয়ার্কার থাকবে, কোন কোন কিউ দেখবে ইত্যাদি।
৩. **Handler:** টাস্ক পেলে আসলে কী কাজ করবে।

```go
srv := asynq.NewServer(
    asynq.RedisClientOpt{Addr: "localhost:6379"},
    asynq.Config{
        Concurrency: 10, // একসাথে ১০টি টাস্ক প্রক্রিয়া করবে
    },
)
```
এখানে `Concurrency: 10` মানে হলো ১০ জন ওয়ার্কার বসে আছে, যারা কিউ থেকে টাস্ক এলেই সেটি তুলে নেবে এবং প্রক্রিয়া করবে।

এবার আসি **Handler**-এর কথায়। এটি হলো সবচেয়ে গুরুত্বপূর্ণ অংশ, যেখানে টাস্কের আসল কাজটি সম্পন্ন হয়। হ্যান্ডলার একটি ইন্টারফেস, যার গঠন নিচের মত:
```go
type Handler interface {
    ProcessTask(context.Context, *asynq.Task) error
}
```
সহজ ভাষায় বললে: সার্ভার তোমাকে টাস্ক দেবে, তুমি সেটা নিয়ে কাজ করবে, এবং শেষে `nil` (সফলতা) অথবা `error` (ব্যর্থতা) রিটার্ন করবে।

হ্যান্ডলার দুইভাবে ইমপ্লিমেন্ট করা যায়:

**১. সাধারণ ফাংশন দিয়ে:**
```go
func handleWelcomeEmail(ctx context.Context, t *asynq.Task) error {
    var payload map[string]interface{}
    json.Unmarshal(t.Payload(), &payload)
    
    fmt.Printf("Sending email to user: %v\n", payload["user_id"])
    // এখানে আসল ইমেইল পাঠানোর কোড থাকবে...
    return nil
}
```

**২. স্ট্রাকট দিয়ে (সুপারিশকৃত):**
বাস্তব অ্যাপ্লিকেশনে হ্যান্ডলারের ডাটাবেস সংযোগ বা অন্যান্য নির্ভরশীলতার প্রয়োজন হয়, তাই স্ট্রাকট ব্যবহার করাই ভালো।
```go
type EmailHandler struct {
    // নির্ভরশীলতা যেমন DB সংযোগ, ইমেইল ক্লায়েন্ট ইত্যাদি
}

func (h *EmailHandler) ProcessTask(ctx context.Context, t *asynq.Task) error {
    var payload map[string]interface{}
    json.Unmarshal(t.Payload(), &payload)
    
    fmt.Printf("Sending email to user: %v\n", payload["user_id"])
    // এখানে DB আপডেট বা ইমেইল পাঠানোর কোড
    return nil
}
```

**ServeMux:** এটি Asynq-এর রাউটার। এটি নির্ধারণ করে কোন টাস্ক টাইপের জন্য কোন হ্যান্ডলার ডাকা হবে।
```go
mux := asynq.NewServeMux()
mux.HandleFunc("email:welcome", handleWelcomeEmail)
mux.HandleFunc("email:reminder", handleReminderEmail)

// সার্ভার চলবে এবং mux অনুযায়ী রাউটিং করবে
if err := srv.Run(mux); err != nil {
    log.Fatal(err)
}
```
সার্ভার যখন টাস্ক তোলে, তখন টাস্কের টাইপ দেখে (`"email:welcome"`) এবং সেটিকে `handleWelcomeEmail` ফাংশনে পাঠিয়ে দেয়।

### সফলতা বনাম ব্যর্থতা (Success vs Failure):

- **`nil` রিটার্ন করলে:** এর অর্থ কাজটি সফলভাবে সম্পন্ন হয়েছে। Asynq বুঝতে পারে "কাজ শেষ"। টাস্কটি Redis থেকে মুছে ফেলা হবে (ডিলিট হয়ে যাবে)। যদি তুমি চাও টাস্কটি কিছুক্ষণ Redis-এ রাখা থাকুক, তাহলে `Retention` অপশন দিতে হবে (পরে আলোচনা করা হবে)।
- **`error` রিটার্ন করলে:** এর অর্থ কাজটি ব্যর্থ হয়েছে। Asynq বুঝতে পারে "কাজ শেষ হয়নি"। টাস্কটি `Retry` স্টেটে চলে যাবে। কিছুক্ষণ অপেক্ষা করার পর আবার চেষ্টা করা হবে। ডিফল্টভাবে এটি ২৫ বার রিট্রাই হবে। ২৫ বার রিট্রাইয়ের পরও যদি কাজ ব্যর্থ হয়, তাহলে টাস্কটি `Archived` স্টেটে চলে যাবে, যাকে আমরা ডেড লেটার কিউ (DLQ) বলতে পারি।

এখন একটি আকর্ষণীয় বিষয়: **`asynq.SkipRetry`**। যদি তুমি নিশ্চিত হও যে একটি টাস্ক পুনরায় চেষ্টা করার কোনো প্রয়োজন নেই (উদাহরণস্বরূপ, Payload-এই ভুল ডাটা আছে এবং রিট্রাই করলেও কখনো সফল হবে না), তাহলে তুমি সরাসরি এটিকে আর্কাইভে পাঠাতে পারো:
```go
func handleWelcomeEmail(ctx context.Context, t *asynq.Task) error {
    var payload map[string]interface{}
    if err := json.Unmarshal(t.Payload(), &payload); err != nil {
        // Payload-এই ভুল, রিট্রাই করে লাভ নেই
        return fmt.Errorf("bad payload: %w", asynq.SkipRetry)
    }
    return nil
}
```
`asynq.SkipRetry` কে wrap করে রিটার্ন করলে টাস্কটি আর রিট্রাই হবে না, সরাসরি আর্কাইভ স্টেটে চলে যাবে।

### সম্পূর্ণ চিত্র (Full Picture):
```
Client                    Redis                    Server
  |                         |                         |
  |-- Enqueue(task) ------->|                         |
  |                         |<-- task তুলে নিল -------|
  |                         |                         |
  |                         |              ServeMux দেখল type
  |                         |              handleWelcomeEmail() call হলো
  |                         |              nil return = success
  |                         |              task delete হলো
```

### গ্রেসফুল শাটডাউন (Graceful Shutdown) এবং সিগন্যাল:
সার্ভার চিরকাল চলতে পারে না, কোনো না কোনো সময় বন্ধ করতে হবে। কিন্তু হঠাৎ বন্ধ করে দিলে কী হবে? ধরো একটি টাস্ক এখনই প্রক্রিয়া হচ্ছে, আর ঠিক তখনই সার্ভার বন্ধ হয়ে গেল। টাস্কটি অসম্পূর্ণ থেকে যাবে। Asynq এই সমস্যার সমাধান করেছে OS সিগন্যালের মাধ্যমে।

দুটি গুরুত্বপূর্ণ সিগন্যাল আছে:
- **TSTP:** "নতুন টাস্ক নেওয়া বন্ধ করো, কিন্তু যে টাস্কগুলো বর্তমানে প্রক্রিয়াধীন আছে, সেগুলো শেষ হতে দাও।"
- **TERM বা INT:** "সবকিছু বন্ধ করো।"

সুপারিশকৃত পদ্ধতি হলো:
```bash
kill -TSTP <pid>   # প্রথমে এটি দাও — নতুন টাস্ক আসা বন্ধ হবে
kill -TERM <pid>   # তারপর এটি দাও — সম্পূর্ণ সার্ভার বন্ধ হবে
```
এই দুই ধাপে বন্ধ করলে চলমান টাস্কগুলো শেষ হওয়ার সুযোগ পাবে। যদি তুমি TSTP না দিয়ে সরাসরি TERM দাও, তাহলে Asynq ৮ সেকেন্ড অপেক্ষা করে। এই ৮ সেকেন্ডের মধ্যে যেসব টাস্ক শেষ হতে পারেনি, সেগুলো আবার `Pending` স্টেটে ফিরে যাবে, যাতে পরে সার্ভার আবার চালু হলে সেগুলো প্রক্রিয়া করা যায়।

এই ৮ সেকেন্ডের সময়সীমা কাস্টমাইজ করা যায়:
```go
asynq.Config{
    ShutdownTimeout: 20 * time.Second, // ৮ সেকেন্ডের পরিবর্তে ২০ সেকেন্ড
}
```

### একটি সম্পূর্ণ উদাহরণ (Client ও Server একত্রে):

**`tasks/tasks.go` - টাস্ক সংজ্ঞা আলাদা প্যাকেজে:**
```go
package tasks

import (
    "context"
    "encoding/json"
    "fmt"
    "github.com/hibiken/asynq"
)

const TypeWelcomeEmail = "email:welcome"

type WelcomeEmailPayload struct {
    UserID int
    Email  string
}

// Client এর জন্য — টাস্ক তৈরি করার ফাংশন
func NewWelcomeEmailTask(userID int, email string) (*asynq.Task, error) {
    payload, err := json.Marshal(WelcomeEmailPayload{
        UserID: userID,
        Email:  email,
    })
    if err != nil {
        return nil, err
    }
    return asynq.NewTask(TypeWelcomeEmail, payload), nil
}

// Server এর জন্য — টাস্ক প্রক্রিয়াকরণের হ্যান্ডলার
func HandleWelcomeEmailTask(ctx context.Context, t *asynq.Task) error {
    var p WelcomeEmailPayload
    if err := json.Unmarshal(t.Payload(), &p); err != nil {
        // Payload ভুল — রিট্রাই করে লাভ নেই
        return fmt.Errorf("bad payload: %w", asynq.SkipRetry)
    }

    // আসল কাজ
    fmt.Printf("Sending welcome email to %s (userID: %d)\n", p.Email, p.UserID)
    return nil // সফল — টাস্ক ডিলিট হবে
}
```

**`client/main.go`:**
```go
package main

import (
    "log"
    "asynq-learning/tasks"
    "github.com/hibiken/asynq"
)

func main() {
    client := asynq.NewClient(asynq.RedisClientOpt{Addr: "localhost:6379"})
    defer client.Close()

    task, err := tasks.NewWelcomeEmailTask(42, "rahim@example.com")
    if err != nil {
        log.Fatal(err)
    }

    info, err := client.Enqueue(task)
    if err != nil {
        log.Fatal(err)
    }

    log.Printf("Task enqueued: id=%s queue=%s state=%s", info.ID, info.Queue, info.State)
}
```

**`server/main.go`:**
```go
package main

import (
    "log"
    "time"
    "asynq-learning/tasks"
    "github.com/hibiken/asynq"
)

func main() {
    srv := asynq.NewServer(
        asynq.RedisClientOpt{Addr: "localhost:6379"},
        asynq.Config{
            Concurrency:     10,
            ShutdownTimeout: 20 * time.Second,
        },
    )

    mux := asynq.NewServeMux()
    mux.HandleFunc(tasks.TypeWelcomeEmail, tasks.HandleWelcomeEmailTask)

    if err := srv.Run(mux); err != nil {
        log.Fatal(err)
    }
}
```
এখানে একটি গুরুত্বপূর্ণ প্যাটার্ন লক্ষ্য করো: টাস্কের টাইপ কনস্ট্যান্ট, Payload স্ট্রাকট, টাস্ক তৈরির ফাংশন এবং হ্যান্ডলার ফাংশন— সবকিছু একটি আলাদা `tasks` প্যাকেজে রাখা হয়েছে। এর কারণ হলো Client ও Server উভয়েরই এই জিনিসগুলোর প্রয়োজন হয়। আলাদা প্যাকেজে রাখলে উভয়েই সেটি ইম্পোর্ট করতে পারে এবং কোডের কোনো পুনরাবৃত্তি হয় না।

এখন পর্যন্ত বেসিক অংশ পুরোপুরি কাভার করা হয়েছে। Client, Task, Server, Handler, ServeMux, Signals—সবকিছু।

## ৪. কিউ অগ্রাধিকার (Queue Priority)

এতক্ষণ আমরা শুধু `default` কিউ নিয়েই কাজ করেছি। সব টাস্ক একই কিউতে যাচ্ছে এবং একই অগ্রাধিকারে প্রক্রিয়া হচ্ছে। কিন্তু বাস্তব জগতে সব টাস্ক সমান গুরুত্বপূর্ণ নয়। ধরো, তোমার সিস্টেমে দুটি কাজ আছে:
- পেমেন্ট কনফার্মেশন ইমেইল — এটি দ্রুত পাঠানো দরকার।
- সাপ্তাহিক নিউজলেটার — এটি একটু দেরি হলেও সমস্যা নেই।

এই দুই কাজ একই কিউতে রাখলে যদি নিউজলেটারের কাজ আগে এসে পড়ে, তাহলে পেমেন্টের ইমেইলটি দেরিতে যাবে, যা ঠিক না। এর সমাধান হলো **একাধিক কিউ ও অগ্রাধিকার** ব্যবহার করা।

Asynq-তে দুইভাবে অগ্রাধিকার দেওয়া যায়:

### ১. ওয়েটেড অগ্রাধিকার (Weighted Priority):
এটি শতকরা হার (Percentage) এর মতো কাজ করে।
```go
srv := asynq.NewServer(
    asynq.RedisClientOpt{Addr: "localhost:6379"},
    asynq.Config{
        Concurrency: 10,
        Queues: map[string]int{
            "critical": 6,
            "default":  3,
            "low":      1,
        },
    },
)
```
এখানে মোট ওয়েট = ৬ + ৩ + ১ = ১০।
এর অর্থ হলো প্রতি ১০টি টাস্ক প্রক্রিয়াকরণের মধ্যে:
- `critical` কিউ থেকে ৬টি
- `default` কিউ থেকে ৩টি
- `low` কিউ থেকে ১টি করে টাস্ক নেওয়া হবে।

এটি একটি ভারসাম্যপূর্ণ পদ্ধতি। `critical` কিউ বেশি মনোযোগ পাচ্ছে, কিন্তু অন্য কিউগুলো একেবারে বাদ পড়ছে না।

### ২. স্ট্রিক্ট অগ্রাধিকার (Strict Priority):
```go
srv := asynq.NewServer(
    asynq.RedisClientOpt{Addr: "localhost:6379"},
    asynq.Config{
        Concurrency: 10,
        Queues: map[string]int{
            "critical": 3,
            "default":  2,
            "low":      1,
        },
        StrictPriority: true, // এটি চালু করতেই হবে
    },
)
```
এক্ষেত্রে সংখ্যাগুলো শুধু ক্রম (Order) বোঝায়, কোনো শতকরা হার নয়। এর অর্থ:
- `critical` কিউ সম্পূর্ণ খালি না হওয়া পর্যন্ত `default` কিউতে হাত দেওয়া হবে না।
- `default` কিউ সম্পূর্ণ খালি না হওয়া পর্যন্ত `low` কিউতে হাত দেওয়া হবে না।

এটি অনেক কঠোর একটি নিয়ম। যদি `critical` কিউতে সবসময় নতুন টাস্ক আসতেই থাকে, তাহলে `low` কিউয়ের টাস্ক কখনোই প্রক্রিয়া নাও হতে পারে। একে বলে **স্টারভেশন (Starvation)**।

**কখন কোনটি ব্যবহার করবে?**
- **Weighted:** যখন সব কিউয়ের টাস্কই ইভেন্টুয়ালি প্রক্রিয়া হওয়া দরকার, শুধু অগ্রাধিকারের তারতম্য আছে।
- **Strict:** যখন ক্রিটিক্যাল টাস্ক নিয়ে কোনো আপস নেই, বাকিগুলো পরে হলেও চলবে।

**Client-এ কিউ নির্ধারণ:**
```go
// critical কিউতে পাঠাও
client.Enqueue(task, asynq.Queue("critical"))

// low কিউতে পাঠাও
client.Enqueue(task, asynq.Queue("low"))

// কিছু না বললে default কিউতে যাবে
client.Enqueue(task)
```
এমনকি টাস্ক তৈরি করার সময়ই ডিফল্ট কিউ নির্ধারণ করে দেওয়া যায়:
```go
// এই টাস্ক সবসময় critical কিউতেই যাবে
task := asynq.NewTask("payment:confirm", payload, asynq.Queue("critical"))
client.Enqueue(task) // আলাদা করে Queue অপশন দিতে হবে না
```

## ৫. টাস্ক রিট্রাই (Task Retry)

বাস্তব জগতে অ্যাপ্লিকেশন সবসময় নিখুঁতভাবে চলে না। নেটওয়ার্ক সমস্যা, বাহ্যিক API-র সাময়িক অপ্রাপ্যতা, অথবা অন্য কোনো কারণে টাস্ক প্রক্রিয়াকরণ ব্যর্থ হতে পারে। এজন্য Asynq ডিফল্টভাবে যেকোনো ব্যর্থ টাস্ক ২৫ বার পুনরায় চেষ্টা (Retry) করে। প্রতিবার রিট্রাইয়ের আগে এটি **এক্সপোনেনশিয়াল ব্যাকঅফ (Exponential Backoff)** অনুসরণ করে অপেক্ষা করে।

**Exponential Backoff কী?** ধরো ইমেইল সার্ভার ডাউন আছে। তুমি যদি প্রতি সেকেন্ডে রিট্রাই করতে থাকো, তাহলে সার্ভারের ওপর চাপ আরও বাড়বে। বরং প্রথমবার ব্যর্থ হলে ১ সেকেন্ড, দ্বিতীয়বার ২ সেকেন্ড, তৃতীয়বার ৪ সেকেন্ড— এভাবে অপেক্ষার সময় বাড়িয়ে দিলে সার্ভার পুনরুদ্ধার হওয়ার সুযোগ পায়।

রিট্রাই কাস্টমাইজ করার চারটি উপায়:

### ১. সর্বোচ্চ রিট্রাই সংখ্যা পরিবর্তন (Max Retry Count):
```go
// টাস্ক তৈরির সময়
task := asynq.NewTask("email:welcome", payload, asynq.MaxRetry(5))
// অথবা Enqueue করার সময়
client.Enqueue(task, asynq.MaxRetry(5))
```
এখন ২৫ বারের পরিবর্তে মাত্র ৫ বার রিট্রাই হবে। রিট্রাই সম্পূর্ণ বন্ধ করতে চাইলে `asynq.MaxRetry(0)` দিতে পারো, তাহলে ব্যর্থ হলেই সরাসরি আর্কাইভে চলে যাবে।

### ২. রিট্রাই বিলম্ব কাস্টমাইজ (Custom Retry Delay):
ডিফল্ট এক্সপোনেনশিয়াল ব্যাকঅফ পছন্দ না হলে নিজস্ব লজিক দেওয়া যায়

### ৩. নন-ফেইলিউর এরর (Non-Failure Error) - রিট্রাই কাউন্ট না কমানো:
কখনো কখনো এরর হয় কিন্তু সেটা টাস্কের দোষ নয়। যেমন: "এই মুহূর্তে রিসোর্স পাওয়া যাচ্ছে না।" এরকম ক্ষেত্রে রিট্রাই কাউন্ট কমানো উচিত নয়, কারণ টাস্কের কোনো সমস্যা নেই। পরবর্তী চেষ্টায় সফল হওয়ার সম্ভাবনা আছে।

### ৪. স্কিপ রিট্রাই (Skip Retry) - সরাসরি আর্কাইভে পাঠানো:
যদি Payload-এই ভুল ডাটা থাকে, তাহলে রিট্রাই করেও কোনো লাভ নেই। বরং সরাসরি আর্কাইভে পাঠিয়ে দাও।
```go
func handleWelcomeEmail(ctx context.Context, t *asynq.Task) error {
    var p WelcomeEmailPayload
    if err := json.Unmarshal(t.Payload(), &p); err != nil {
        // Payload-ই ভুল, রিট্রাই করা বোকামি
        return fmt.Errorf("invalid payload: %w", asynq.SkipRetry)
    }
    return nil
}
```

### রিট্রাইয়ের সম্পূর্ণ ফ্লো (Full Retry Flow):
```
Handler error return করল
        ↓
IsFailure() check করল — এটা কি সত্যিকারের ব্যর্থতা?
   না হলে → retry count না কমিয়ে আবার Pending
   হলে → retry count কমানো হলো
        ↓
SkipRetry wrap করা আছে?
   হ্যাঁ → সরাসরি Archived
   না → Retry state-এ গেল
        ↓
MaxRetry শেষ হয়ে গেছে?
   হ্যাঁ → Archived
   না → কিছুক্ষণ পরে আবার Pending
```

## ৬. টাইমআউট ও বাতিলকরণ (Timeout & Cancellation)

ধরো তোমার একটি টাস্ক আছে যেটি একটি এক্সটার্নাল API কল করে। কিন্তু সেই API কোনো রেসপন্স দিচ্ছে না, ফলে টাস্কটি আটকে আছে এবং ওয়ার্কার ব্লক হয়ে বসে আছে। এই ওয়ার্কার আর অন্য কোনো টাস্ক প্রক্রিয়া করতে পারছে না। এটাই হলো **টাইমআউট**-এর প্রয়োজনীয়তা।

টাইমআউট দুইভাবে দেওয়া যায়:

### ১. টাইমআউট (Timeout) - হ্যান্ডলার শুরু হওয়ার পর থেকে সময় গণনা:
```go
// টাস্ক তৈরির সময়
task := asynq.NewTask("email:welcome", payload, asynq.Timeout(30*time.Second))
// অথবা Enqueue-র সময়
client.Enqueue(task, asynq.Timeout(30*time.Second))
```
এর মানে হলো হ্যান্ডলার শুরু হওয়ার ৩০ সেকেন্ডের মধ্যে কাজ শেষ করতে হবে। না হলে Asynq হ্যান্ডলারের `context` ক্যান্সেল করে দেবে।

### ২. ডেডলাইন (Deadline) - নির্দিষ্ট সময়ের আগে শেষ করতে হবে:
```go
// ২০২৫ সালের ৩১ ডিসেম্বরের আগে শেষ করতে হবে
deadline := time.Date(2025, time.December, 31, 0, 0, 0, 0, time.UTC)
client.Enqueue(task, asynq.Deadline(deadline))
```
পার্থক্য: `Timeout` আপেক্ষিক (Relative), হ্যান্ডলার শুরু হওয়ার পর থেকে গণনা হয়। আর `Deadline` পরম (Absolute), একটি নির্দিষ্ট সময় নির্ধারণ করে দেয়।

### হ্যান্ডলারে Context-কে সম্মান করা:
শুধু টাইমআউট দিয়ে দিলেই হবে না, হ্যান্ডলারকে `context`-এর ক্যান্সেলেশন সিগন্যাল শুনতে হবে। নয়তো টাইমআউট সেট করেও হ্যান্ডলার চলতেই থাকবে এবং ওয়ার্কার আটকে থাকবে।

**ভুল পদ্ধতি:**
```go
func handleTask(ctx context.Context, t *asynq.Task) error {
    // context-এর কথা ভুলে গেছি
    // টাইমআউট হলেও এই ফাংশন চলতেই থাকবে
    result := doHeavyWork()
    return nil
}
```

**সঠিক পদ্ধতি:**
```go
func handleTask(ctx context.Context, t *asynq.Task) error {
    // একটি চ্যানেলে কাজের ফলাফল আসবে
    resultChan := make(chan error, 1)

    go func() {
        resultChan <- doHeavyWork() // ব্যাকগ্রাউন্ডে ভারী কাজ চলছে
    }()

    select {
    case err := <-resultChan:
        // কাজ শেষ হয়েছে
        return err
    case <-ctx.Done():
        // টাইমআউট বা ক্যান্সেলেশন হয়েছে
        return ctx.Err()
    }
}
```
এখানে `select` স্টেটমেন্ট দিয়ে আমরা দুটি চ্যানেল পর্যবেক্ষণ করছি। কাজ শেষ হলে রেজাল্ট আসবে, আর টাইমআউট হলে `ctx.Done()` চ্যানেলটি বন্ধ হয়ে যাবে। যেটি আগে ঘটবে, সেটিই বিজয়ী হবে।

### Context থেকে তথ্য সংগ্রহ:
হ্যান্ডলারের ভেতরে `context` থেকে অনেক দরকারি তথ্য জানা যায়:
```go
func handleTask(ctx context.Context, t *asynq.Task) error {
    // এই টাস্কের আইডি জানা যায়
    taskID, _ := asynq.GetTaskID(ctx)

    // কতবার রিট্রাই হয়েছে জানা যায়
    retryCount, _ := asynq.GetRetryCount(ctx)

    // সর্বোচ্চ কতবার রিট্রাই হবে জানা যায়
    maxRetry, _ := asynq.GetMaxRetry(ctx)

    fmt.Printf("Processing task %s (retry %d/%d)\n", taskID, retryCount, maxRetry)
    return nil
}
```
এটি কাজে আসে কারণ রিট্রাই কাউন্ট দেখে তুমি বুঝতে পারো এটি প্রথমবার চলছে নাকি রিট্রাই স্টেটে আছে। সেই অনুযায়ী তুমি তোমার লজিক ভিন্ন করতে পারো।

### ম্যানুয়াল ক্যান্সেলেশন (CLI দিয়ে):
চলমান কোনো অ্যাক্টিভ টাস্ক তুমি চাইলে ম্যানুয়ালি বাতিল করতে পারো:
```bash
# প্রথমে অ্যাক্টিভ টাস্কগুলোর তালিকা দেখো
asynq task ls --queue=default --state=active

# তারপর নির্দিষ্ট আইডির টাস্কটি ক্যান্সেল করো
asynq task cancel <task_id>
```
এটি করলে সেই টাস্কের `context` ক্যান্সেল হয়ে যাবে। হ্যান্ডলার যদি সঠিকভাবে `context` শোনে, তাহলে সে কাজ বন্ধ করবে এবং `error` রিটার্ন করবে। টাস্কটি আবার `Retry` স্টেটে চলে যাবে।

## ৭. পর্যায়ক্রমিক কাজ (Periodic Tasks)

মনে করো তোমার কিছু কাজ আছে যা নির্দিষ্ট সময় পরপর চালাতে হবে। যেমন:
- প্রতিদিন রাত ১২টায় নিষ্ক্রিয় ইউজারদের রিমাইন্ডার ইমেইল পাঠানো।
- প্রতি ঘণ্টায় ডাটাবেস ক্লিনআপ করা।
- প্রতি সোমবার সকালে উইকলি রিপোর্ট জেনারেট করা।

এগুলো হলো **পর্যায়ক্রমিক টাস্ক (Periodic Tasks)**। Asynq-তে এর জন্য আলাদা একটি উপাদান আছে, যার নাম **Scheduler**।

### শিডিউলার (Scheduler) কীভাবে কাজ করে?
Scheduler সার্ভারের সাথে একই প্রসেসে বা আলাদা প্রসেসে চলতে পারে। এর কাজ একটাই: নির্দিষ্ট সময়ে টাস্ক তৈরি করে কিউতে পাঠিয়ে দেওয়া। তারপর সার্ভার সেটি তুলে নিয়ে প্রক্রিয়া করবে।

```
Scheduler → নির্দিষ্ট সময়ে → কিউতে টাস্ক দেয়
Server → কিউ থেকে টাস্ক তুলে → প্রক্রিয়া করে
```

### ক্রন সিনট্যাক্স (Cron Syntax):
`"* * * * *"` - এই ফরম্যাটটি একটি ক্রন এক্সপ্রেশন।
```
* * * * *
| | | | |
| | | | └── সপ্তাহের দিন (0-6, রবিবার=0)
| | | └──── মাস (1-12)
| | └────── মাসের দিন (1-31)
| └──────── ঘণ্টা (0-23)
└────────── মিনিট (0-59)
```
কিছু উদাহরণ:
```go
"* * * * *"        // প্রতি মিনিটে
"0 * * * *"        // প্রতি ঘণ্টায় (ঘণ্টার শুরুতে)
"0 0 * * *"        // প্রতিদিন রাত ১২টায়
"0 9 * * 1"        // প্রতি সোমবার সকাল ৯টায়
"0 0 1 * *"        // প্রতি মাসের ১ তারিখে
"@every 30s"       // প্রতি ৩০ সেকেন্ডে
"@every 1h"        // প্রতি ঘণ্টায়
"@every 24h"       // প্রতি ২৪ ঘণ্টায়
```

### টাইমজোন (Timezone):
ডিফল্ট UTC টাইম ব্যবহার করা হয়। বাংলাদেশি সময়ে করতে চাইলে:
```go
loc, err := time.LoadLocation("Asia/Dhaka")
if err != nil {
    log.Fatal(err)
}

// এখন রাত ১২টা মানে ঢাকার রাত ১২টা
scheduler.Register("0 0 * * *", task)
```

### অপশনসহ রেজিস্টার:
```go
scheduler.Register(
    "0 9 * * 1",
    task,
    asynq.Queue("critical"), // ক্রিটিক্যাল কিউতে পাঠাও
    asynq.MaxRetry(3),       // সর্বোচ্চ ৩ বার রিট্রাই
)
```

### এরর হ্যান্ডলিং:
শিডিউলার যদি কোনো কারণে টাস্ক কিউতে দিতে ব্যর্থ হয়, তাহলে সেটি হ্যান্ডেল করা যায়:

### একটি গুরুত্বপূর্ণ সতর্কতা:
শিডিউলার একটিই চালাতে হবে। যদি তুমি ৩টি মেশিনে তোমার অ্যাপ ডেপ্লয় করো এবং প্রতিটিতে যদি শিডিউলার চালু থাকে, তাহলে একই টাস্ক ৩ বার কিউতে জমা হবে। এটি একটি বড় সমস্যা (Duplicate Problem)। সমাধান হলো: শিডিউলারকে একটি আলাদা প্রসেস হিসেবে শুধুমাত্র একটি মেশিনে চালানো। যেমন:
```
machine 1: go run server/main.go    ← টাস্ক প্রক্রিয়া করে
machine 2: go run server/main.go    ← টাস্ক প্রক্রিয়া করে (স্কেল করার জন্য)
machine 3: go run scheduler/main.go ← শুধু একটি চলবে, যা টাস্ক তৈরি করবে
```

## ৮. রেট লিমিটিং (Rate Limiting)

ধরো তোমার হ্যান্ডলারে একটি এক্সটার্নাল ইমেইল সার্ভিসের API কল হয়। সেই API-র ডকুমেন্টেশন বলে: "প্রতি সেকেন্ডে সর্বোচ্চ ১০টি রিকোয়েস্ট করতে পারবে।" কিন্তু তোমার কিউতে ১০০০টি টাস্ক পেন্ডিং আছে। সার্ভার একসাথে সবগুলো প্রক্রিয়া করতে গেলে API-র রেট লিমিট অতিক্রম করবে এবং API এরর দেবে। টাস্কগুলো ব্যর্থ হবে, রিট্রাই হবে, এবং পুরো সিস্টেম অকার্যকর হয়ে যাবে। এর সমাধানই হলো **রেট লিমিটিং**।

### Asynq-তে রেট লিমিটিং কীভাবে কাজ করে:
Asynq নিজে সরাসরি রেট লিমিটিং করে না। বরং এটি একটি চমৎকার প্যাটার্ন প্রদান করে: **`rate.Limiter`-এর সাথে নন-ফেইলিউর এরর** (যা আমরা আগে দেখেছি)।

এর লজিকটি হলো:
1. রেট লিমিট অতিক্রম করেছে কিনা চেক করো।
2. যদি অতিক্রম করে থাকে → নন-ফেইলিউর এরর রিটার্ন করো (যার ফলে রিট্রাই কাউন্ট কমবে না, কিছুক্ষণ পরে আবার চেষ্টা হবে)।
3. যদি অতিক্রম না করে থাকে → কাজ করো এবং `nil` রিটার্ন করো।

### ধাপ ১: `golang.org/x/time/rate` প্যাকেজ ইনস্টল
```bash
go get golang.org/x/time/rate
```

### ধাপ ২: লিমিটার তৈরি করো
```go
import "golang.org/x/time/rate"

// প্রতি সেকেন্ডে ১০টি রিকোয়েস্ট, সর্বোচ্চ ১০টি বার্স্ট (একসাথে জমা রাখতে পারবে)
limiter := rate.NewLimiter(rate.Every(time.Second/10), 10)
```
- প্রথম প্যারামিটার `rate`: প্রতি সেকেন্ডে কতটি অনুমোদন করবে।
- দ্বিতীয় প্যারামিটার `burst`: হঠাৎ করেই সর্বোচ্চ কতটি অনুমোদন করবে (টোকেন বাকেটের সাইজ)।


### সম্পূর্ণ ফ্লো বোঝা যাক:
```
Queue তে ১০০০ টাস্ক আছে
        ↓
Worker টাস্ক তুলল
        ↓
limiter.Allow() চেক করল
   false → ErrRateLimitExceeded রিটার্ন করল
           IsFailure() → false (ব্যর্থতা নয়)
           রিট্রাই কাউন্ট কমল না
           কিছুক্ষণ পরে আবার Pending হবে
   true  → কাজ করল
           nil রিটার্ন করল
           টাস্ক ডিলিট হলো
```

এমনকি তুমি কিউ-ভিত্তিক রেট লিমিটিংও করতে পারো:
```go
type EmailHandler struct {
    limiters map[string]*rate.Limiter
}

func (h *EmailHandler) ProcessTask(ctx context.Context, t *asynq.Task) error {
    queueName, _ := asynq.GetQueueName(ctx)
    limiter := h.limiters[queueName]
    if limiter != nil && !limiter.Allow() {
        return ErrRateLimitExceeded
    }
    // কাজ করো...
    return nil
}
```

## ৯. ইউনিক টাস্ক (Unique Tasks) ও ডুপ্লিকেট প্রতিরোধ

ধরো, একজন ইউজার "Resend Email" বাটনে ক্লিক করল। নেটওয়ার্ক স্লো থাকায় সে অধৈর্য হয়ে বাটনটি ৫ বার ক্লিক করল। তোমার কিউতে এখন একই ইমেইল পাঠানোর জন্য ৫টি টাস্ক জমা হলো। ফলে ইউজার ৫টি ইমেইল পাবে, যা একটি বিরক্তিকর অভিজ্ঞতা। এটি প্রতিরোধ করতেই **ইউনিক টাস্ক**-এর প্রয়োজন।

Asynq-তে দুটি উপায়ে এটি করা যায়:

### ১. টাস্ক আইডি (TaskID) দিয়ে (১০০% গ্যারান্টিযুক্ত):
তুমি নিজেই একটি ইউনিক আইডি তৈরি করে দেবে। একই আইডি দিয়ে দ্বিতীয়বার Enqueue করতে গেলে এরর আসবে।
```go
// প্রথমবার — সফল
_, err := client.Enqueue(task, asynq.TaskID("welcome-email-user-42"))

// দ্বিতীয়বার — ব্যর্থ
_, err = client.Enqueue(task, asynq.TaskID("welcome-email-user-42"))
if errors.Is(err, asynq.ErrTaskIDConflict) {
    log.Println("Task already exists!")
}
```
এটি ১০০% গ্যারান্টিযুক্ত। যতক্ষণ পর্যন্ত এই আইডির টাস্কটি Redis-এ আছে (Pending, Active, Retry, Archived যেকোনো স্টেটেই থাকুক না কেন), ততক্ষণ একই আইডি দিয়ে আর কোনো টাস্ক ঢুকতে পারবে না। টাস্ক সম্পন্ন হয়ে ডিলিট হয়ে গেলে পরবর্তীতে আবার একই আইডি ব্যবহার করা যাবে।

### ২. ইউনিক অপশন (Unique) দিয়ে (সর্বোত্তম প্রচেষ্টা / Best Effort):
এখানে তুমি নিজে আইডি বানাও না। Asynq নিজেই টাস্কের **Type + Payload + Queue** এই তিনটির সমন্বয়ে একটি লক তৈরি করে।
```go
// t1 কিউতে গেল, ১ ঘণ্টার জন্য লক নিল
_, err := client.Enqueue(t1, asynq.Unique(time.Hour))

// t2 একই type + payload + queue — ডুপ্লিকেট!
_, err = client.Enqueue(t2, asynq.Unique(time.Hour))
if errors.Is(err, asynq.ErrDuplicateTask) {
    log.Println("Duplicate task, skipped!")
}
```
লক কখন মুক্তি পায়?
- টাস্ক সফলভাবে প্রক্রিয়া হলে।
- নির্ধারিত TTL (এখানে ১ ঘণ্টা) শেষ হয়ে গেলে।

যেটি আগে ঘটবে, সেটিই কার্যকর হবে।

### গুরুত্বপূর্ণ সতর্কতা: ইউনিক অপশন ১০০% গ্যারান্টিযুক্ত নয়।
এটি "বেস্ট-এফোর্ট" পদ্ধতি। কেন? কারণ যদি লকের TTL শেষ হয়ে যায়, কিন্তু টাস্কটি তখনও পেন্ডিং বা অ্যাক্টিভ থাকে, তাহলে আবার একই টাস্ক জমা দেওয়া সম্ভব। উদাহরণস্বরূপ, যদি কোনো কাজ প্রক্রিয়া করতে ২ ঘণ্টা লাগে, কিন্তু তুমি `Unique` অপশনে TTL দিয়েছ ১ ঘণ্টা, তাহলে ১ ঘণ্টা পর লক চলে যাবে এবং দ্বিতীয় একটি টাস্ক কিউতে ঢুকে যেতে পারবে, যদিও প্রথমটি এখনো শেষ হয়নি।

সুতরাং:
- **১০০% গ্যারান্টি দরকার:** `TaskID` ব্যবহার করো।
- **বেস্ট-এফোর্ট যথেষ্ট:** `Unique` ব্যবহার করো।

**কখন কোনটি ব্যবহার করবে?**
| পরিস্থিতি | সমাধান |
| :--- | :--- |
| একই ইউজারকে দুইবার ইমেইল যাবে না | `TaskID` দাও ইউজারের আইডি দিয়ে |
| একই পেমেন্ট দুইবার প্রক্রিয়া হবে না | `TaskID` দাও পেমেন্ট আইডি দিয়ে |
| উচ্চ ট্রাফিকে ডুপ্লিকেট প্রতিরোধ করতে চাও | `Unique` দাও TTL সহ |
| পর্যায়ক্রমিক টাস্ক ডুপ্লিকেট না হোক | `Unique` যথেষ্ট |

**বিশ্লেষণ:** `TaskID` কঠোর (strict) এবং `Unique` নরম (best-effort)। যখন আমরা মিনিট প্যাকেজ কিনি, তখন পেমেন্ট গেটওয়েতে `TaskID` ব্যবহার করা হয় যেন একই ট্রানজেকশন দুইবার চার্জ না হয়। আর "এই মুভি দেখুন" বাটনের ক্ষেত্রে (যা একটি ব্যাকগ্রাউন্ড টাস্ক না হয়ে রিয়েল-টাইম অ্যাকশন) সাধারণত ইউনিক টাস্কের প্রয়োজন হয় না, তবে যদি অ্যানালিটিক্স ইভেন্ট পাঠানো হয়, তাহলে `Unique` ব্যবহার করে অল্প সময়ের মধ্যে ডুপ্লিকেট ইভেন্ট আটকানো যায়।

## ১০. টাস্ক সংরক্ষণ ও ফলাফল (Task Retention & Result)

ডিফল্টভাবে টাস্ক সফলভাবে সম্পন্ন হলে Redis থেকে সাথে সাথে মুছে যায় এবং কোনো রেকর্ড থাকে না। কিন্তু কিছু ক্ষেত্রে এর প্রয়োজন হতে পারে:
- টাস্ক সম্পন্ন হওয়ার পরও কিছুক্ষণ রেখে দিতে চাও, যেন পরিদর্শন (Inspection) করতে পারো।
- টাস্কের ফলাফল (Result) সংরক্ষণ করতে চাও, যেন পরে সেটি পড়তে পারো।

### টাস্ক রিটেনশন (Task Retention):
```go
// টাস্ক সম্পন্ন হওয়ার পর ২৪ ঘণ্টা Redis-এ রাখবে
client.Enqueue(task, asynq.Retention(24 * time.Hour))
```
এটি করলে টাস্ক সম্পন্ন হওয়ার পর `Completed` স্টেটে চলে যাবে এবং ২৪ ঘণ্টা পর স্বয়ংক্রিয়ভাবে মুছে যাবে। এই সময়ের মধ্যে তুমি CLI বা ওয়েব UI দিয়ে সেটি দেখতে পারবে।
```bash
asynq task ls --queue=default --state=completed
```

### টাস্ক রেজাল্ট (Task Result):
টাস্ক প্রক্রিয়াকরণের সময় হ্যান্ডলার কিছু ডাটা সংরক্ষণ করতে পারে।

### রিটেনশন ও রেজাল্ট একসাথে:
```go
client.Enqueue(task, asynq.Retention(2*time.Hour)) // ২ ঘণ্টা ধরে রাখবে
// হ্যান্ডলারে result.Write() করে ফলাফল জমা রাখা
```
২ ঘণ্টার মধ্যে যেকোনো সময় ফলাফল পড়া যাবে।

### কখন দরকার হয়?
- **Retention:** যখন অডিট ট্রেইল (কোন টাস্ক কখন শেষ হয়েছে) দরকার, অথবা ডিবাগ করতে চাও, অথবা ক্লায়েন্টকে জানাতে চাও টাস্ক সম্পন্ন হয়েছে কিনা।
- **Result:** যখন ব্যাকগ্রাউন্ডে কোনো কিছু জেনারেট করা হয়েছে (যেমন ফাইলের URL) এবং ক্লায়েন্ট পরে এসে ফলাফল নেবে (পোলিং প্যাটার্ন)।

### একটি সতর্কতা:
রেজাল্ট Redis-এ সংরক্ষিত হয় এবং Redis মেমোরি সীমিত। তাই বড় ডাটা (যেমন সম্পূর্ণ ফাইল) কখনো রেজাল্ট হিসেবে সংরক্ষণ করবে না। বড় ডাটার জন্য S3 বা ডাটাবেস ব্যবহার করো এবং রেজাল্টে শুধু তার রেফারেন্স (যেমন S3 URL) রাখো।

```go
// ভালো পদ্ধতি
t.ResultWriter().Write([]byte(`{"s3_url": "https://..."}`))

// খারাপ পদ্ধতি (Redis-এ চাপ সৃষ্টি করবে)
t.ResultWriter().Write(entireFileBytes) // ❌
```

**তবে বাস্তব অ্যাপ্লিকেশনে সাধারণত যা হয়:** বেশিরভাগ ক্ষেত্রেই `Retention` ও `Result` ব্যবহার না করাই ভালো। কারণ প্রায় সব অ্যাপ্লিকেশনেরই একটি স্থায়ী ডাটাবেস (যেমন PostgreSQL) থাকে। টাস্ক শেষ হলে ডাটাবেসে `task completed, result: xyz` এন্ট্রি করে দেওয়াই উত্তম। এটি পারসিস্টেন্ট, মেমোরি লিমিটেড নয়, এবং কমপ্লেক্স কোয়েরি করা যায়। সুতরাং, Retention ও Result তখনই ব্যবহার করো যখন সত্যিই প্রয়োজন, নয়তো স্থায়ী ডাটাবেসের ওপর নির্ভর করো।

## ১১. টাস্ক অ্যাগ্রিগেশন (Task Aggregation)

ধরো তোমার অ্যাপে একটি নোটিফিকেশন সিস্টেম আছে। ১ মিনিটের মধ্যে একজন ইউজারের জন্য ১০০টি নোটিফিকেশন আসল। যদি প্রতিটি নোটিফিকেশনের জন্য আলাদা ইমেইল পাঠাও, তাহলে ইউজার বিরক্ত হবে এবং স্প্যাম মনে করবে। বরং ভালো হয় ১০০টি নোটিফিকেশন একসাথে "ব্যাচ" করে একটি ইমেইলে পাঠানো: "আপনার ১০০টি নতুন নোটিফিকেশন আছে।" এটাই হলো **টাস্ক অ্যাগ্রিগেশন**।

### এটি কীভাবে কাজ করে:
- **ক্লায়েন্ট সাইড:** টাস্কগুলো একই কিউ এবং একই গ্রুপে পাঠাতে হবে।
- **সার্ভার সাইড:** `GroupAggregator` ফাংশন দিতে হবে, যা একাধিক টাস্ককে একত্রিত করে একটি নতুন টাস্ক তৈরি করবে।

তিনটি শর্তের যেকোনো একটি পূরণ হলে অ্যাগ্রিগেশন ঘটে:
1. **গ্রেস পিরিয়ড শেষ:** নতুন টাস্ক আসা বন্ধ হওয়ার পর কিছুক্ষণ অপেক্ষা করে।
2. **সর্বোচ্চ বিলম্ব শেষ:** যতই টাস্ক আসুক, এই সময়ের পরে জোর করে অ্যাগ্রিগেশন হয়।
3. **সর্বোচ্চ আকার পূর্ণ:** নির্দিষ্ট সংখ্যক টাস্ক জমলেই অ্যাগ্রিগেশন হয়।

### ক্লায়েন্ট সাইড উদাহরণ:
```go
// তিনটি নোটিফিকেশন টাস্ক — একই কিউ ও গ্রুপে
client.Enqueue(task1, asynq.Queue("notifications"), asynq.Group("user-42-email"))
client.Enqueue(task2, asynq.Queue("notifications"), asynq.Group("user-42-email"))
client.Enqueue(task3, asynq.Queue("notifications"), asynq.Group("user-42-email"))
```
`Group` নামটি গুরুত্বপূর্ণ। একই গ্রুপের টাস্কগুলো একসাথে অ্যাগ্রিগেট হবে। ভিন্ন ভিন্ন ইউজারের জন্য ভিন্ন গ্রুপ ব্যবহার করতে হবে।


### গ্রেস পিরিয়ডের বাস্তব উদাহরণ:
```
user-42 এর নোটিফিকেশন আসল        → টাইমার শুরু (২ মিনিট)
৩০ সেকেন্ড পরে আরেকটি আসল        → টাইমার রিসেট (আবার ২ মিনিট)
আরও ৩০ সেকেন্ড পরে আরেকটি আসল   → টাইমার রিসেট (আবার ২ মিনিট)
২ মিনিট কোনো নতুন টাস্ক আসেনি     → অ্যাগ্রিগেট করো!
```
কিন্তু যদি প্রতি ৩০ সেকেন্ডে টাস্ক আসতেই থাকে, তাহলে `GroupMaxDelay` (১০ মিনিট) শেষে জোর করে অ্যাগ্রিগেশন হবে।

### একটি সতর্কতা:
**শিডিউলিং (`ProcessIn`/`ProcessAt`) এবং অ্যাগ্রিগেশন একসাথে কাজ করে না।**
```go
// এটি কাজ করবে না, শিডিউলিং প্রাধান্য পাবে
client.Enqueue(task, asynq.Group("user-42-email"), asynq.ProcessIn(1*time.Hour)) // ❌
```

### কখন অ্যাগ্রিগেশন দরকার?
- ইউজারকে ব্যাচ নোটিফিকেশন পাঠাতে চাইলে।
- ডাটাবেসে এককভাবে ইনসার্ট না করে বাল্ক ইনসার্ট করতে চাইলে।
- বাহ্যিক API কল কমাতে চাইলে।

## ১২. প্রোডাকশন সেটআপ: রেডিস ক্লাস্টার ও অটোমেটিক ফেইলওভার

এতক্ষণ আমরা একটি মাত্র Redis সার্ভার ব্যবহার করেছি (localhost:6379)। কিন্তু প্রোডাকশনে একটি মাত্র Redis সার্ভার থাকা মানেই বিপদ। যদি সেটি ডাউন হয়ে যায়, তাহলে পুরো সিস্টেম অচল হয়ে যাবে। কোনো টাস্ক Enqueue হবে না, প্রক্রিয়াও হবে না। একে বলে **সিঙ্গেল পয়েন্ট অফ ফেইলিউর (Single Point of Failure)**।

এর সমাধান দুটি:
1. **Redis Cluster:** একাধিক Redis নোড, ডাটা শার্ডিং।
2. **Redis Sentinel:** অটোমেটিক ফেইলওভার।

এই দুটি সম্পূর্ণ আলাদা জিনিস। আগে পার্থক্যটা বুঝি:

- **Redis Cluster:** ডাটা একাধিক নোডে ভাগ করে রাখে (শার্ডিং)। এটি **হরাইজন্টাল স্কেলিং**-এর জন্য। অনেক বেশি ডাটা হ্যান্ডেল করতে পারে। একটি নোড ডাউন হলে বাকিগুলো কাজ চালিয়ে যেতে পারে।
- **Redis Sentinel:** ডাটা একটি নোডে (মাস্টার) থাকে, বাকিগুলো তার রেপ্লিকা। মাস্টার ডাউন হলে স্বয়ংক্রিয়ভাবে একটি রেপ্লিকাকে মাস্টার বানিয়ে ফেলে। এটি **হাই অ্যাভেইলেবিলিটি**-র জন্য, স্কেলিংয়ের জন্য নয়।

### Redis Cluster সেটআপ:
```go
srv := asynq.NewServer(
    asynq.RedisClusterClientOpt{
        Addrs: []string{
            "redis-node-1:6379",
            "redis-node-2:6379",
            "redis-node-3:6379",
        },
    },
    asynq.Config{Concurrency: 10},
)

client := asynq.NewClient(asynq.RedisClusterClientOpt{
    Addrs: []string{...},
})
```

### গুরুত্বপূর্ণ সতর্কতা (Redis Cluster-এ Asynq-এর সীমাবদ্ধতা):
Asynq অভ্যন্তরীণভাবে Lua স্ক্রিপ্ট ব্যবহার করে। Redis Cluster-এ Lua স্ক্রিপ্ট নিয়ে সমস্যা হতে পারে যদি স্ক্রিপ্টটি একাধিক কী অ্যাক্সেস করে এবং সেই কীগুলো ভিন্ন ভিন্ন নোডে থাকে। তাই Redis Cluster-এ Asynq ব্যবহারের আগে অবশ্যই ভালো করে পরীক্ষা করে নিতে হবে।

### অটোমেটিক ফেইলওভার - Redis Sentinel (সুপারিশকৃত):
প্রোডাকশনের জন্য সবচেয়ে সুপারিশকৃত পদ্ধতি হলো Redis Sentinel।

কীভাবে কাজ করে:
```
Master Redis (সব রাইট এখানে)
    ↓ replicate
Replica 1 (রিড করা যায়)
Replica 2 (রিড করা যায়)

Sentinel 1 }
Sentinel 2 } ← মাস্টারকে পর্যবেক্ষণ করে
Sentinel 3 }

মাস্টার ডাউন হলে → সেন্টিনেলরা ভোট করে → একটি রেপ্লিকা নতুন মাস্টার হয়।
```

## ১৪. মিডলওয়্যার (Middleware)

ধরো তোমার ১০টি হ্যান্ডলার আছে। প্রতিটি হ্যান্ডলারে তুমি চাও:
- কাজ শুরু ও শেষের সময় লগ করো।
- কোনো প্যানিক হলে রিকভার করো।
- কোন ইউজারের টাস্ক তা ট্র্যাক করো।

এই কাজগুলো যদি প্রতিটি হ্যান্ডলারে আলাদাভাবে লেখো, তাহলে একই কোড বারবার লেখা হবে (Duplication)। মিডলওয়্যার এই সমস্যার সমাধান করে। একবার লিখে সব হ্যান্ডলারে প্রয়োগ করা যায়।

### মিডলওয়্যার কী?
মিডলওয়্যার হলো এমন একটি ফাংশন যা:
1. হ্যান্ডলার চালানোর **আগে** কিছু কাজ করে।
2. হ্যান্ডলারকে কল করে।
3. হ্যান্ডলার চালানোর **পরে** কিছু কাজ করে।

এটি পেঁয়াজের স্তরের মতো (Onion Layers):
```
Request আসল
    ↓
Middleware 1 শুরু
    ↓
Middleware 2 শুরু
    ↓
Actual Handler চলল
    ↓
Middleware 2 শেষ
    ↓
Middleware 1 শেষ
```

### মিডলওয়্যার প্রয়োগের পদ্ধতি:

**সকল হ্যান্ডলারে প্রয়োগ:**
```go
mux := asynq.NewServeMux()
mux.Use(loggingMiddleware)    // সব হ্যান্ডলারে লাগবে
mux.Use(recoveryMiddleware)   // সব হ্যান্ডলারে লাগবে
mux.HandleFunc("email:welcome", handleWelcomeEmail)
```

**নির্দিষ্ট হ্যান্ডলারে প্রয়োগ:**
```go
mux.Handle(
    "email:welcome",
    loggingMiddleware(asynq.HandlerFunc(handleWelcomeEmail)),
)
```

**গ্রুপ মিডলওয়্যার:**
```go
// ইমেইল সম্পর্কিত কাজের জন্য আলাদা মিডলওয়্যার
emailMux := asynq.NewServeMux()
emailMux.Use(emailRateLimitMiddleware)
emailMux.HandleFunc("email:welcome", handleWelcomeEmail)

// পেমেন্ট সম্পর্কিত কাজের জন্য আলাদা মিডলওয়্যার
paymentMux := asynq.NewServeMux()
paymentMux.Use(transactionMiddleware(db))
paymentMux.HandleFunc("payment:process", handlePayment)

// সব একত্রে
mainMux := asynq.NewServeMux()
mainMux.Use(loggingMiddleware)
mainMux.Use(recoveryMiddleware)
mainMux.Handle("email:", emailMux)     // email:* → emailMux
mainMux.Handle("payment:", paymentMux) // payment:* → paymentMux
```

### মিডলওয়্যারের ক্রম (Order) গুরুত্বপূর্ণ:
```go
mux.Use(loggingMiddleware)   // প্রথমে
mux.Use(recoveryMiddleware)  // দ্বিতীয়তে
```
এই ক্রমে চলবে: logging শুরু → recovery শুরু → হ্যান্ডলার → recovery শেষ → logging শেষ। যদি উল্টো করো, তাহলে প্যানিক হলে logging মিডলওয়্যার ক্র্যাশ করত এবং রিকভারি তখনো আসত না।

## ১৫. গুরুত্বপূর্ণ জরুরি প্রশ্নোত্তর (Critical Production Q&A)

এখানে কিছু গুরুত্বপূর্ণ প্রশ্নের উত্তর দেওয়া হলো, যা প্রোডাকশন সিস্টেম ডিজাইনের সময় জানা জরুরি।

### ১. ওয়ার্কার ক্র্যাশ করলে কী হয়?
**ম্যানুয়াল পদ্ধতি (চ্যানেল/গোরুটিন):**
```go
func worker(jobs <-chan int) {
    for userID := range jobs {
        processJob(userID) // এখানে ক্র্যাশ করলে?
    }
}
```
ওয়ার্কার ক্র্যাশ করলে কাজটি হারিয়ে যায়। কেউ জানতে পারে না। কোনো রিকভারি নেই।

**Asynq পদ্ধতি:**
Asynq "অন্তত একবার ডেলিভারি" (At-least-once delivery) গ্যারান্টি দেয়। কিভাবে? যখন কোনো ওয়ার্কার টাস্ক তোলে, তখন সেটি `Pending` লিস্ট থেকে সরে `Active` সেটে চলে যায়। Redis থেকে ডিলিট হয় না। Asynq-এর একটি ব্যাকগ্রাউন্ড প্রসেস নিয়মিত চেক করে "কোনো টাস্ক অনেকক্ষণ ধরে অ্যাক্টিভ সেটে পড়ে আছে কিনা"। থাকলে সেটিকে আবার `Pending` স্টেটে ফিরিয়ে দেয়। এই টাইমআউট কনফিগার করা যায় `ShutdownTimeout` দিয়ে। তাই ওয়ার্কার ক্র্যাশ করলেও টাস্ক হারায় না।

### ২. কিভাবে নিশ্চিত করবে যে একাধিক ওয়ার্কার একই টাস্ক প্রক্রিয়া করছে না?
Asynq-তে টাস্ক তোলার সময় Redis-এর `BRPOPLPUSH` বা সমতুল্য অ্যাটমিক অপারেশন ব্যবহার করা হয়। একটি টাস্ক একবার `Active` সেটে গেলে সেটি আর অন্য কোনো ওয়ার্কারকে দেওয়া হয় না। যতক্ষণ না প্রথম ওয়ার্কারটি ব্যর্থ হয় বা টাইমআউট হয়, ততক্ষণ এটি দ্বিতীয় ওয়ার্কারের কাছে যাবে না। সুতরাং, ডুপ্লিকেট প্রক্রিয়াকরণ স্বয়ংক্রিয়ভাবে প্রতিরোধ করা হয়।

### ৩. ডেড লেটার কিউ (DLQ) বা আর্কাইভড টাস্ক কিভাবে হ্যান্ডেল করবে?
সর্বোচ্চ রিট্রাই শেষে টাস্ক `Archived` স্টেটে চলে যায়। এগুলো হারিয়ে যায় না। তুমি তিনটি কাজ করতে পারো:
1. **পরিদর্শন করো:** কেন ব্যর্থ হলো তা বোঝার জন্য CLI বা ওয়েব UI দিয়ে দেখো।
   ```bash
   asynq task ls --queue=default --state=archived
   ```
   কোডে: `inspector.ListArchivedTasks("default")`
2. **ম্যানুয়ালি পুনরায় চালাও:** বাগ ঠিক করার পর আর্কাইভ থেকে আবার রান করাতে পারো।
   ```bash
   asynq task run --queue=default --id=<task_id>
   # অথবা সবগুলো একসাথে
   asynq task run --queue=default --state=archived --all
   ```
3. **মুছে ফেলো:** যদি টাস্কটি আর দরকার না হয়।
   ```bash
   asynq task delete --queue=default --state=archived --all
   ```

**প্রোডাকশন প্যাটার্ন:**
সাধারণত আর্কাইভড টাস্কের জন্য `ErrorHandler`-এ অ্যালার্ট কনফিগার করা হয় (স্ল্যাক, ইমেইল)। ডেভেলপার অ্যালার্ট পেয়ে কারণ অনুসন্ধান করে, প্রয়োজনে বাগ ফিক্স করে এবং তারপর আর্কাইভড টাস্কগুলো ম্যানুয়ালি রি-রান করিয়ে দেয়।

### সারাংশ (Manual vs Asynq):

| সমস্যা | ম্যানুয়াল পদ্ধতি | Asynq পদ্ধতি |
| :--- | :--- | :--- |
| **ওয়ার্কার ক্র্যাশ** | কাজ হারিয়ে যায় | অ্যাক্টিভ সেট থেকে আবার পেন্ডিং-এ ফিরে আসে |
| **ডুপ্লিকেট টাস্ক** | নিজেকে ট্র্যাক করতে হয় | TaskID বা Unique অপশন |
| **ব্যর্থ টাস্ক** | নিজেকে হ্যান্ডেল করতে হয় | আর্কাইভড স্টেট, ম্যানুয়ালি রান বা ডিলিট |
| **একই টাস্ক মাল্টিপল ওয়ার্কার** | সম্ভব (রেস কন্ডিশন) | অ্যাটমিক অপারেশনের মাধ্যমে প্রতিরোধ |
